# Autoresearch for AIO Skills

스킬은 대부분 70% 정도 작동한다. 나머지 30%는 쓰레기가 나온다. 해결책은 스킬을 처음부터 재작성하는 것이 아니다. 에이전트가 스킬을 수십 번 실행하고, 모든 출력을 채점하고, 프롬프트를 조금씩 바꾸어 그 30%를 제거하게 하는 것이다.

이 스킬은 Andrej Karpathy의 autoresearch 방법론(자율 실험 루프)을 Claude Code 스킬에 적용한다.

---

## 핵심 작업

기존 스킬을 가져와서 "좋은 출력"이 무엇인지를 바이너리 yes/no 체크로 정의한 뒤, 아래를 반복하는 자율 루프를 실행:

1. 테스트 입력으로 스킬 출력 생성
2. 평가 기준(evals)으로 모든 출력 채점
3. 실패를 고치기 위해 스킬 프롬프트를 단 하나만 변경
4. 점수가 오른 변경은 유지, 떨어지면 롤백
5. 점수 상한에 도달하거나 사용자가 멈출 때까지 반복

**출력:** 개선된 SKILL.md + `results.tsv` 로그 + `changelog.md` + 실시간 HTML 대시보드

---

## 시작 전: 컨텍스트 수집

**STOP. 아래 항목이 모두 확인될 때까지 실험을 시작하지 않는다. 누락된 항목은 사용자에게 먼저 확인.**

1. **대상 스킬** — 어떤 스킬을 최적화할 것인가? (SKILL.md 경로)
2. **테스트 입력** — 스킬을 테스트할 3~5개 시나리오 (다양성이 중요 — 단일 케이스 과적합 방지)
3. **평가 기준** — 좋은 출력을 정의하는 3~6개 바이너리 yes/no 체크 (eval-guide.md 참조)
4. **실험당 실행 횟수** — 기본값: 5회 (5가 대부분의 스킬에서 최적)
5. **실험 간격** — 기본값: 2분
6. **예산 상한** — 선택사항. 최대 실험 사이클 수 (기본: 무제한)

---

## 1단계: 스킬 읽기

변경 전에 대상 스킬을 완전히 읽고 이해한다.

1. SKILL.md 전체 읽기
2. `references/`의 파일 읽기
3. 스킬의 핵심 작업, 단계, 출력 형식 파악
4. 기존 품질 체크 및 안티패턴 파악

이 단계를 건너뛰지 않는다. 스킬을 이해하지 않고는 개선할 수 없다.

---

## 2단계: Eval 스위트 구축

사용자의 평가 기준을 구조화된 테스트로 변환한다. 모든 체크는 바이너리여야 한다 — 통과 또는 실패, 척도 없음.

**각 eval 형식:**

```
EVAL [번호]: [짧은 이름]
질문: [yes/no 질문]
통과 조건: [yes가 의미하는 것 — 구체적으로]
실패 조건: [no를 유발하는 것 — 구체적으로]
```

**좋은 eval 규칙:**
- 바이너리만. yes 또는 no. "1~7점 척도" 없음. 척도는 가변성을 증폭시켜 신뢰할 수 없는 결과를 낸다.
- 일관성 있게 채점할 수 있을 만큼 구체적. "텍스트가 읽기 좋은가?"는 너무 모호. "모든 단어 철자가 올바르고 문장이 잘리지 않았는가?"는 테스트 가능.
- 3~6개가 최적. 그 이상이면 스킬이 eval 기준만 앵무새처럼 반복하기 시작.

**최대 점수 계산:**
```
max_score = [eval 수] × [실험당 실행 횟수]
```

자세한 내용은 [references/eval-guide.md](references/eval-guide.md) 참조.

---

## 3단계: 실시간 대시보드 생성

실험 시작 전 `autoresearch-[skill-name]/dashboard.html` 생성 후 브라우저에서 열기.

대시보드 필수 요소:
- 10초마다 자동 새로고침 (results.json 읽기)
- 점수 진행 꺾은선 차트 (X축: 실험 번호, Y축: 통과율 %)
- 각 실험별 색상 바: 초록=유지, 빨강=폐기, 파랑=기준선
- 실험별 테이블: 실험#, 점수, 통과율, 상태, 설명
- eval별 분석: 어떤 eval이 가장 자주 통과/실패하는지
- 현재 상태: "실험 [N] 실행 중..." 또는 "대기"

단일 HTML 파일, 인라인 CSS/JS. 차트에는 CDN의 Chart.js 사용.

**results.json 형식:**
```json
{
  "skill_name": "[이름]",
  "status": "running",
  "current_experiment": 3,
  "baseline_score": 70.0,
  "best_score": 90.0,
  "experiments": [
    {"id": 0, "score": 14, "max_score": 20, "pass_rate": 70.0, "status": "baseline", "description": "원본 스킬 — 변경 없음"}
  ],
  "eval_breakdown": [
    {"name": "eval 이름", "pass_count": 8, "total": 10}
  ]
}
```

## 4단계: 기준선 측정

변경 전에 스킬을 있는 그대로 실행. 이것이 실험 #0.

1. 작업 디렉토리 생성: `autoresearch-[skill-name]/`
2. 원본 SKILL.md를 `[사용자-지정-이름].md`로 복사 — 이것만 변경. 원본 SKILL.md는 절대 수정하지 않음.
3. `SKILL.md.baseline`도 저장 (롤백 대상)
4. results.tsv + results.json + dashboard.html 생성
5. 테스트 입력으로 스킬 [N]회 실행
6. 모든 출력을 모든 eval로 채점
7. 기준선 점수 기록

**results.tsv 형식 (탭 구분):**
```
experiment	score	max_score	pass_rate	status	description
0	14	20	70.0%	baseline	원본 스킬 — 변경 없음
```

**기준선 확인 후 진행**: 기준선이 이미 90%+이면 사용자에게 계속할지 확인.

---

## 5단계: 실험 루프

루프가 시작되면 중단 조건에 도달할 때까지 자율 실행.

**LOOP:**

1. **실패 분석.** 어떤 eval이 가장 자주 실패하는가. 실제로 실패한 출력을 읽어라. 패턴 파악 — 포맷 문제인가? 누락된 지시사항인가? 모호한 지시사항인가?

2. **가설 수립.** 변경할 **하나의 항목** 선택. 5가지를 동시에 바꾸지 않는다 — 무엇이 도움이 됐는지 알 수 없다.

   좋은 변경:
   - 가장 흔한 실패를 다루는 구체적인 지시사항 추가
   - 모호한 지시사항을 더 명확하게 재작성
   - 반복되는 실수에 대한 안티패턴 추가 ("X를 절대 하지 말 것")
   - 묻혀있는 중요한 지시사항을 앞으로 이동 (우선순위 = 위치)
   - 올바른 동작을 보여주는 예시 추가 또는 개선
   - 하나의 기준만 최적화하게 만드는 지시사항 제거

   나쁜 변경:
   - 전체 스킬 재작성
   - 동시에 10개 새 규칙 추가
   - 구체적 이유 없이 스킬 길이 늘리기
   - "더 잘해" 또는 "더 창의적으로" 같은 모호한 지시사항

3. **변경 적용.** `[사용자-지정-이름].md` 편집. 원본 SKILL.md는 절대 건드리지 않음.

4. **실험 실행.** 동일한 테스트 입력으로 스킬 [N]회 실행.

5. **채점.** 모든 출력을 모든 eval로 채점. 총점 계산.

6. **유지 또는 폐기.**
   - 점수 향상 → **유지.** 기록. 이것이 새 기준선.
   - 점수 동일 → **폐기.** 이전 버전으로 롤백. 복잡성만 추가.
   - 점수 하락 → **폐기.** 이전 버전으로 롤백.

7. **결과 기록** in results.tsv.

8. **반복.** 루프 1번으로 돌아가기.

**멈추지 않는다.** 루프가 시작되면 중단 조건 전까지 자율 실행:
- 사용자가 수동 중지
- 예산 상한 도달
- 3번 연속 95%+ 통과율 (수익 감소)

---

## 6단계: 변경 기록 작성

각 실험 후 `changelog.md`에 추가:

```markdown
## 실험 [N] — [유지/폐기]

**점수:** [X]/[max] ([percent]%)
**변경:** [변경한 내용 한 문장]
**근거:** [왜 이 변경이 도움이 될 것으로 예상했는가]
**결과:** [실제로 일어난 것 — 어떤 eval이 향상/저하]
**여전히 실패:** [아직 실패하는 것, 있다면]
```

이 changelog가 가장 가치 있는 산출물이다. 어떤 미래 에이전트(또는 더 스마트한 모델)도 이어서 최적화할 수 있는 연구 로그.

---

## 7단계: 결과 전달

사용자가 돌아오거나 루프가 멈추면:

1. **점수 요약:** 기준선 → 최종 점수 (향상 %)
2. **총 실험 횟수:** 시도한 변경 수
3. **유지율:** 유지 vs 폐기 비율
4. **도움이 된 상위 3개 변경**
5. **남은 실패 패턴**
6. **개선된 [사용자-지정-이름].md** (작업 디렉토리 내)
7. results.tsv + changelog.md 위치

## AIO 스킬 후보 및 권장 Eval 기준

### /integrate (최고 우선순위)
```
EVAL 1: 키워드 추가
질문: TECH_KW 또는 MACRO_KW에 3개 이상의 신규 키워드가 추가되었는가?
통과: 새 키워드 블록에 ≥3개 항목
실패: 추가된 키워드 <3개 또는 기존 중복

EVAL 2: 티커 메모 갱신
질문: 원문에서 핵심적으로 언급된 주요 티커 중 ≥1개가 SCREENER_DB에서 갱신되었는가?
통과: 최소 1개 티커 메모에 신규 인사이트 반영
실패: 티커가 원문에 있는데 SCREENER_DB 갱신 없음

EVAL 3: CHAT_CONTEXTS 업데이트
질문: 관련 CHAT_CONTEXTS 섹션(macro/technical/sector 중 해당)이 업데이트되었는가?
통과: 해당 섹션에 신규 내용 추가
실패: CHAT_CONTEXTS 변경 없음

EVAL 4: CHANGELOG 기록
질문: CHANGELOG.md에 이번 통합에 대한 항목이 추가되었는가?
통과: 버전 항목 + 변경 내용 기술
실패: CHANGELOG 갱신 없음

EVAL 5: R17 준수
질문: 추가된 모든 키워드가 3글자 이상인가?
통과: 모든 신규 키워드 ≥3글자
실패: 1글자 또는 2글자 단독 키워드 존재
```

### /data-refresh (2순위)
```
EVAL 1: 전수 스캔
질문: 22개 카테고리 전체에 대한 staleness 테이블이 출력되었는가?
통과: 22개 행 포함 테이블

EVAL 2: CRITICAL 항목 처리
질문: CRITICAL 판정 항목이 모두 업데이트되었는가?
통과: CRITICAL 항목 0개 미처리

EVAL 3: 배열 길이 검증
질문: labels20/vixData/hyData 길이가 일치하는가?
통과: 세 배열 길이 동일

EVAL 4: 버전 범프
질문: 6곳 버전 동기화가 완료되었는가?
통과: title/badge/APP_VERSION/version.json/CLAUDE.md/CHANGELOG 일치
```

### /qa (3순위)
```
EVAL 1: div 균형
질문: <div> 수와 </div> 수가 일치하는가?
통과: 정확히 일치

EVAL 2: 버전 6곳 동기화
질문: 6곳 버전 문자열이 동일한가?
통과: 모두 동일

EVAL 3: Dead Page 없음
질문: 21개 페이지 중 빈 화면(Dead Page)이 없는가?
통과: 모든 페이지 정상

EVAL 4: 뉴스 스코어링
질문: 기업 뉴스 score ≥30, 매크로 뉴스에 ETF 티커 미표시가 확인되었는가?
통과: 두 조건 모두 충족
```

## 출력 파일 구조

```
autoresearch-[skill-name]/
├── dashboard.html        # 실시간 브라우저 대시보드 (10초 자동 새로고침)
├── results.json          # 대시보드 데이터 파일
├── results.tsv           # 모든 실험 점수 로그
├── changelog.md          # 상세 변경 로그
└── SKILL.md.baseline     # 최적화 전 원본 (롤백 대상)
```

**원본 SKILL.md는 절대 수정하지 않는다.** 개선된 버전은 `[사용자-지정-이름].md`에 존재.
