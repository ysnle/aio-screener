# Eval Guide (AIO 스킬용)

실제로 스킬 품질을 개선하는 바이너리 평가 기준을 작성한다. 거짓 자신감을 만드는 척도나 느낌 검사를 사용하지 않는다.

## 평가 원칙

1. 모든 eval을 yes/no 질문으로 작성한다.
2. 두 평가자가 같은 증거를 보고 같은 판정을 내릴 수 있게 만든다.
3. 스킬이 실제 품질 개선 없이 문구만 맞춰 통과할 수 없게 만든다.
4. 사용자가 실제로 신경 쓰는 결과를 관찰 가능한 신호로 바꾼다.
5. 서로 겹치지 않는 핵심 eval 3~6개만 유지한다.

## 평가 모드

- **정적 계약 평가**: frontmatter, 라우터 크기, 참조 존재, command 연결, 미러 parity처럼 파일로 판정 가능한 구조를 검사한다.
- **행동 평가**: 실제 사용자 프롬프트를 실행한 출력의 정확성, 누락, 형식, 안전 경계를 검사한다.
- 정적 평가만 실행했다면 프롬프트 품질이나 실제 작업 성공률이 개선됐다고 주장하지 않는다.

## 좋은 eval과 나쁜 eval

| 나쁜 질문 | 좋은 질문 |
|-----------|-----------|
| 분석이 충분히 심층적인가? | Q1~Q5 중 원문에 근거한 프레임워크와 무효화 조건이 각각 기록됐는가? |
| 데이터가 최신인가? | 각 갱신값에 관측시각, 출처, sourceKind가 있고 CRITICAL 미처리가 0건인가? |
| QA가 철저한가? | 변경 위험에 매핑된 필수 tier가 모두 실행되거나 BLOCKED로 기록됐는가? |
| 스킬 구조가 좋은가? | 라우터가 90줄 이하이고 모든 직접 참조와 command wrapper가 존재하는가? |
| 버전이 맞는가? | `ci-version-check.mjs`가 R1 7개 표면을 통과했는가? |
| 모든 페이지가 정상인가? | 현재 route registry에서 파생한 대상 라우트가 각각 명시적 PASS/FAIL/BLOCKED를 갖는가? |

## 흔한 실패

- 1~7점 척도처럼 채점자마다 달라지는 기준.
- 정확히 3개 티커처럼 실제 품질과 무관한 고정 개수.
- 같은 조건을 다른 문장으로 두 번 세는 중복 eval.
- 사용자가 유용하다고 느낄지처럼 에이전트가 측정할 수 없는 질문.
- 현재 route 수, 과거 버전, 특정 날짜를 영구 상수로 박아 두는 평가.
- 정적 구조 PASS를 실제 브라우저·네트워크·사용자 작업 성공으로 승격하는 평가.

## 확정 전 3단계 테스트

1. 다른 평가자가 같은 증거로 같은 결과를 낼 수 있는가?
2. 스킬이 실제 개선 없이 이 eval만 게임할 수 있는가?
3. 실패했을 때 어떤 지시·참조·게이트를 바꿀지 명확한가?

## 템플릿

```text
EVAL [N]: [짧은 이름]
질문: [yes/no 질문]
통과: [관찰 가능한 증거]
실패: [구체적인 반례 또는 누락]
증거: [명령, 파일, 출력 또는 실행 trace]
```

예시:

```text
EVAL 1: Canonical/mirror parity
질문: 로컬 `.agents/skills`가 canonical `.claude/skills`와 byte-synchronized 상태인가?
통과: `node scripts/sync-agent-skills.mjs --check` exit 0
실패: 누락, 추가 또는 내용 불일치 파일이 1개 이상
증거: sync check stdout와 exit code
```
