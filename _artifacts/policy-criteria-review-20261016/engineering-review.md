## 주요 의미·논리 발견

### E01 · P2 · 의미 검수를 위한 게이트가 감사 수와 영구 미인증을 보존한다

근거: R219(_context/RULES.md:2741), R220(:2761), scripts/ci-semantic-review-check.mjs:60~70. 현재 gate는 auditDefs>=50, auditLikeLabels>=100, shapeOnlyLabels>=50을 요구하고, coverage.releaseCertified===false를 통과 조건으로 둔다. 구조 검사 수가 많아도 의미 인증이 아니라는 경고는 올바르지만, 수량 하한을 강제하면 감사 코드를 정리하거나 실제 인수를 완료할 때 오히려 gate를 깨뜨린다. 과거 coverage 파일 경로(:26)는 현재 검토 범위의 증거를 대신하지 못한다.

반례: 같은 행동을 더 잘 검증하는 회귀 10개로 중복 shape-only 검사 60개를 대체하면 품질이 개선돼도 하한 때문에 실패한다. 실제 의미 인수를 완료해 releaseCertified=true로 바꿔도 현재 조건은 실패한다. 이는 실행하지 않고 조건문으로 확인한 논리 반례다.

대안/부작용: 검사 개수의 하한을 제거하고, 중요한 주장별 실제 부정 대조·관찰 범위·증거 시점과 source identity를 검증한다. 미인증 상태를 정직하게 보존하되 영구 false를 요구하지 않는다. 덜 중요한 감사의 제거가 쉬워지는 대신, “핵심 행동이 정말 남았는가”를 변경 리뷰에서 확인해야 한다.

수용 기준: 중복 검사 삭제는 통과하고 핵심 의미 반례 삭제는 실패한다. 미인증·부분 인수·정식 범위 인수를 각각 적합한 증거와 함께 표현할 수 있어야 한다. 분류: QA 경험칙/증거 설계이며 법적 요구가 아니다.

### E02 · P2 · 모든 결함을 규칙·원장·새 검사로 누적하는 것은 비용 대비 선별이 부족하다

근거: AGENTS.md:61, R3(:2272), R25(:2360), WORKFLOW-GOVERNANCE.md:94~102, knowledge-lint/references/workflow.md:16~18. 재발을 막는 회귀와 추적은 유용하다. 그러나 모든 버그의 개별 P, 반복 실패의 gate 의무, 모든 지침의 binary self-eval, 규칙 위반 3회의 강화 플래그가 결합되면 사람의 유지 부담과 형식 검사가 계속 늘어난다.

반례: 접근 이름 오타 한 건이나 삭제된 기능의 문구 정리를 위해 새 원장 항목·새 assertion·도입 릴리스 추적을 각각 쌓아도 다음 사용자 실패를 더 잘 탐지하지 못할 수 있다. 반대로 금고 데이터 유실·다른 issuer 오매핑은 단 한 번이어도 회귀가 필요하다. 빈도 3회는 위험도나 검사 경제성을 대신하지 않는다.

대안/부작용: 심각도·재발 가능성·실제 관찰 가능성·검사 유지 비용으로 선택한다. 같은 원인의 배치 기록과 기존 행동 회귀 확장을 우선하고, 중요한 단발성 결함은 즉시 회귀한다. 절차를 줄이면 빠뜨릴 위험이 있으므로 최소 기록은 증상/원인/반례/변경/확인 범위로 유지한다.

수용 기준: 5개 대표 작업(문구 정리, UI 누락, 데이터 오염, 배포 drift, 금고 손실)을 넣었을 때 필요한 증거가 다르게 선택되고, 사소한 작업에 추가 gate를 만들지 않아도 합법적인 완료 경로가 있어야 한다. 분류: 운영 경험칙.

### E03 · P2 · 기준선은 시간 차이이고 파일 소유권은 아니다

근거: AGENTS.md:7,71, QA-PIPELINE-ARCHITECTURE.md:34~37, post-edit-qa/SKILL.md:28, scripts/qa-runner.mjs:273~289. session baseline은 시작 전 dirty와 이후 변경을 구분하지만, 이후 다른 사람이 바꾼 파일도 해시 차이로 들어온다. “이번 작업만 격리”라고 읽히는 설명은 병행 작업에서 과하다.

반례: A가 baseline을 잡은 뒤 B가 다른 파일을 편집하면 A의 affected에 B의 파일도 들어온다. 이미 dirty인 같은 파일에 두 사람이 덧붙여도 baseline만으로 줄 단위 소유권을 나눌 수 없다.

대안/부작용: 병행 편집은 소유 파일 목록 또는 worktree를 사용한다. session은 변경 탐지, owned-paths는 작업 경계로 구별한다. 경로 교집합만으로는 공유 helper의 소비자를 빠뜨릴 수 있으므로 QA 영향 확장은 여전히 필요하다.

수용 기준: A/B의 독립 변경 fixture에서 A의 “내 파일 목록”과 “검사할 공유 소비자”가 구분되며, B의 작업을 A의 수정/완료로 보고하지 않아야 한다. 분류: 협업/도구 계약.

### E04 · P2 · 전면 생산기 금지는 파일 접두사가 아니라 효과로 분류해야 한다

근거: AGENTS.md:35는 fetch/build/sync/refresh의 로컬 실행을 금지하지만 :62,81~82는 sync-agent-*와 workspace 생성/확인을 요구한다. data-refresh/SKILL.md:28과 references/workflow.md:9~12는 dispatch와 무조건 버전 bump를 안내한다. WORKFLOW-GOVERNANCE.md:203은 dispatch의 명시 권한도 요구한다.

반례: 네트워크를 쓰지 않고 fixture를 임시 디렉터리에 만드는 build 함수와, 실제 공급자 quota를 쓰고 public-data를 덮는 fetch는 위험이 다르다. sync-agent-skills --check도 접두사만 보면 금지되고 필수 마감 규칙에서는 요구된다. “새로고침”이 곧 production workflow dispatch 권한인지도 지침 사이에 해석 여지가 있다.

대안/부작용: (a) 외부 수집/청구/production artifact 쓰기, (b) 로컬 결정적 문서 생성, (c) fixture/읽기 전용 검사를 분리한다. (a)의 단일 운영 경계는 유지하고, (b)(c)는 명시 output 경로·네트워크 없음·tracked data 불변 조건으로 허용한다. 앱 코드 version, 데이터 revision/asOf, 문서 수정일을 구별한다. 분류가 늘지만 무의미한 승인과 위험한 예외 추론을 줄인다.

수용 기준: 명령 예시별 허용 효과와 금지 효과가 명확하고 --check/fixture와 production 쓰기 모두 반례로 검증된다. 실제 dispatch는 사용자 요청의 운영 범위에 포함되는지 판단해야 한다. 분류: 권한/운영 정책.

### E05 · P2 · main 직접 작업과 무조건 pull은 공유 작업 트리에서 충분한 안전 규칙이 아니다

근거: AGENTS.md:64~66. 한 운영자의 작은 일반 변경에서 main 직접 작업은 PR 운영 비용을 줄인다. 그러나 “parallel agents 때만 branch”와 “push 전 git pull --no-rebase”를 보편적인 안전 절차로 삼을 수 없다.

반례: 사용자 dirty와 bot data commit이 함께 있는 때 pull이 거부되거나 내용 충돌이 생길 수 있다. 수동 수정·버전 생성·기록을 먼저 마친 뒤 pull/merge가 코드를 바꾸면 앞서 확보한 QA 증거는 합쳐진 결과에 그대로 적용되지 않는다. 정확한 SHA 인증이 이 마지막 경계를 대신해야 한다.

대안/부작용: 먼저 fetch로 원격 차이를 확인하고 작업 소유권·생성물 충돌을 분류한다. 병행/장시간/많은 dirty 작업은 전용 worktree를 기본 후보로 삼되 사소한 단독 작업에 강제하지 않는다. merge 후 바뀐 입력만 다시 선택해 검증하고 최종 index와 증거를 묶는다. worktree는 디스크·환경 복제 비용이 있으므로 무조건 branch/PR로 바꾸자는 제안은 아니다.

수용 기준: unrelated dirty·bot data advance·shared-shell advance·생성물 충돌 시나리오에서 무관 변경 보존, 최종 검증 대상, push 대상이 명확해야 한다. 분류: Git 운영 경험칙.

### E06 · P2 · 구현 수단을 절대화한 페이지 갱신 규칙이 native lifecycle과 충돌한다

근거: R9(:2305), R15(:2315), R187(:2707), R189(:2710), ADR-0001:20~31. 페이지마다 legacy init/pageShown/liveQuotes 3종을 강제하거나 매 진입 최신 artifact reload를 요구하면 정적 지식·분기 공시·공유 캐시까지 불필요한 갱신이 늘 수 있다. 매 merge가 legacy를 src로 이전해야 한다는 AGENTS.md:38도 관련 없는 수정에 이관을 끼워 넣을 위험이 있다.

반례: guide나 이미 받은 같은 13F shard는 시세 tick과 무관하다. 반대로 화면이 떠 있는 동안 원천이 새로 발행되면 “진입 시만 reload”로는 부족하다. listener의 존재는 UI가 맞는 자료를 읽는다는 증거도 아니다.

대안/부작용: route의 데이터 의존성·게시 revision/ETag·원천 발행 주기·mount/dispose를 계약으로 삼는다. 해당 변경으로 대체한 legacy만 제거하며 다른 작업까지 이관하지 않는다. 캐시 설계는 무효화 실수를 만들 수 있으므로 게시 revision 변경·LKG·이탈 취소를 행동으로 검증한다.

수용 기준: 같은 revision의 정적 자료는 재요청하지 않고, 새 발행 자료는 필요한 활성 소비자만 갱신하며, 이탈 후 쓰기·중복 타이머는 0이어야 한다. 분류: 성능/현재성 경험칙.

### E07 · P2 · 병렬 fallback 강제는 가장 싼/믿을 수 있는 성공을 보장하지 않는다

근거: R156(:2161)는 Promise.race 오류를 바로잡았지만 Promise.any 병렬 fallback을 규칙으로 지정한다. per-attempt timeout과 provider budget 조건은 좋은 제한이나, fan-out이 항상 필요한 것은 아니다.

반례: 공식 제공처가 200ms 후 응답하고 약한 proxy가 50ms 후 정상 모양의 오래된 값을 주면 first success가 가장 나쁜 자료가 될 수 있다. 두 요청이 모두 quota를 소비하며 Promise.any 자체는 패배 요청을 취소하지 않는다. 하나가 캐시/LKG로 충분하면 병렬 요청은 순수 비용이다.

대안/부작용: 원천 권위·의미 검증·cache·속도 목표·quota에 따라 순차 또는 제한적 지연 hedge를 고른다. admission 뒤 의미 검증을 통과한 결과만 채택하고 나머지는 취소한다. 순차는 지연이 늘 수 있으므로 실제 deadline 안에서 비교한다.

수용 기준: 빠른 stale/오매핑 응답이 느린 공식 유효 응답을 이기지 않으며, 취소·동시 요청 수·공급자 비용이 설정한 한도 안에 있어야 한다. 분류: 네트워크 경험칙.

### E08 · P2 · 숫자 렌더링 규칙의 Number 정규화는 결측을 0으로 만들 수 있다

근거: R230 첫 항목(_context/RULES.md:2134)은 Number(...) + Number.isFinite(...)를 권장한다. R15(:2315)의 결측/0 분리 원칙과 충돌한다. Number(null), Number(''), Number(false)는 유한한 0이다.

반례: API에서 null인 이익·시세를 Number로 먼저 바꾸면 화면은 오류 없이 0.00을 그린다. 크래시를 막았지만 데이터 의미는 틀린다. 직접 .toFixed 문자열 금지 검사가 이 오표시를 잡지는 못한다.

대안/부작용: 기존 도메인 숫자 헬퍼와 schema 계약에서 null/blank/boolean을 먼저 구분하고 유효 0은 보존한다. 0이 유효한 수익률과 0이 불가능한 가격은 별도 domain constraint다. 예외 처리 코드를 화면마다 복제하지 않는다.

수용 기준: null/undefined/빈 문자열/false/NaN/Infinity/정상 0/숫자 문자열의 출력과 보류 이유를 각 필드 의미대로 검증한다. 분류: 데이터 무결성/언어 동작.

### E09 · P2 · 자동 적용되는 검토 명령이 이미 승인된 작업을 다시 멈출 수 있다

근거: AGENTS.md:54, CLAUDE.md:79는 assumptions/trim/retro를 상시 루틴으로 연결한다. .claude/commands/assumptions.md:12는 무조건 stop, trim-pr.md:13~14는 적용 전 승인을 요구하고 retro.md:17~18도 재승인을 요구한다. bug-fix/SKILL.md:25는 subagent가 수정하지 못한다고 하면서 일반 worker 위임 원칙과 다르다.

반례: 사용자가 범위와 자율 수정을 승인했는데 가정 목록을 작성했다는 이유로 다시 멈추는 것은 추가 안전 정보 없이 지연만 만든다. /assumptions만 명시 호출한 사용자가 실제 수정을 기대하지 않는 경우에는 stop이 맞다. 두 상황을 구분해야 한다.

대안/부작용: 독립적인 “검토만” 명령은 read-only를 유지하고, 이미 승인된 구현의 내부 단계로 사용할 때는 확인 가능한 가정은 검증 후 진행한다. 권한이 없는 비가역·유료·기능 삭제 결정은 실제 변경안을 준비한 뒤 요청한다. reviewer와 편집 worker의 역할을 분리해 disjoint ownership에 한해 위임한다. 자동 진행 범위를 넓히면 오판 위험이 있으므로 권한 출처·수정 범위는 계속 명시한다.

수용 기준: “가정만 보여줘”는 멈추고, “알아서 고치고 검증해”는 승인된 범위 내 진행하며, 두 경우 모두 push/deploy를 별도 승인 없이 하지 않아야 한다. 분류: 협업/권한 정책.

### E10 · P2 · 바이너리 실험 점수의 개선만으로 스킬 품질을 판단하면 과적합된다

근거: autoresearch/SKILL.md:12,39, references/workflow.md:48~54, eval-guide.md:7. 같은 3~5프롬프트에 3~6 yes/no 지표를 반복 적용하고 같거나 나쁘면 폐기하며 95%를 세 번 넘으면 종료한다. 작은 절차 개선의 탐색에는 저렴하지만 독립 품질 증거로는 약하다.

반례: 동일 점수에서 토큰/시간을 절반으로 줄이는 개선을 자동 거절한다. 알려진 프롬프트에만 맞춘 문구가 점수를 올려도 보지 못한 질문은 나빠질 수 있다. 모델 출력 변동과 평가자 불일치를 한 번의 yes/no로 처리하면 작은 차이를 개선으로 오인한다. 단일 변수 실험은 상호작용을 놓칠 수도 있다. NIST는 OFAT의 이 한계를 설명한다: [NIST one-variable-at-a-time](https://www.itl.nist.gov/div898/handbook/pri/section2/pri212.htm).

대안/부작용: 안전/정확성은 binary 필수 조건으로 두고 완성률·시간·비용은 별도 기록한다. 같은 품질·더 작은 비용도 채택 가능하게 한다. 개발 prompt와 보류 prompt를 나누고 일부만 독립 반복/블라인드 검토한다. 큰 통계 플랫폼이나 전 조합 실험은 5명 앱에 과하다. 간단한 paired 소수 표본부터 충분하다.

수용 기준: 알려진 prompt 전용 꼼수가 holdout에서 탈락하고, 동등 품질의 비용 절감은 채택되며, 결과를 재현 환경·표본수·미검증과 함께 보고해야 한다. 분류: 실험 설계 경험칙.

### E11 · P2 · 검증 지도와 형식 marker를 제품의 정답으로 승격하지 않아야 한다

근거: verify-aio/features/README.md:3은 map이 spec이고 script가 drift라고 한다. 유지보수 skill은 app regression과 doc drift를 구별하도록 하지만, map 자체도 최신 사용자 요구나 제품 결정보다 우선할 수 없다. R231(:2113)은 시각 위계를 actual marker로 닫도록 요구한다. marker의 존재는 사용자가 결론을 찾고 이해한다는 증거가 아니다.

반례: 의도적인 탭 이름 개선 후 map을 정답으로 고정하면 올바른 제품을 구이름으로 되돌릴 수 있다. 글자 수가 충분하고 DOM에 결론 카드가 있어도 잘못된 신용 원인·분모를 읽게 할 수 있다. fresh context별 feature PASS는 cross-feature 상태 유지까지 인증하지 않는다.

대안/부작용: 사용자 목적/승인된 계약→map→driver 순서를 명시하고 실패를 제품 회귀/지도 drift/driver 결함/환경 미충족으로 분리한다. 최소 대표 end-to-end 동선과 reload/복구를 추가한다. 테스트가 길어질 수 있으므로 기존 중복 경로를 통합해 시간을 확보한다.

수용 기준: 승인된 rename을 제품 회귀로 잘못 분류하지 않고, marker만 맞춘 잘못된 의미 출력은 실제 행동/값 비교에서 실패해야 한다. 분류: QA 증거 설계.

### E12 · P3 · UX 상수와 접근성 표준은 별도 층이어야 한다

근거: R51(:2535), design-review.md:8,16,21~23. 3~5줄·130~230자·항상 visual+text·emoji 금지·12px/10px·44px은 대부분 제품 선호나 내부 휴리스틱이다. 모든 섹션에 강제하면 짧은 확인문에도 불필요한 그림과 설명을 만든다. 같은 design checklist의 비검증 grade를 description으로 허용하는 문장은 AGENTS.md:32의 grade 제한과도 적용 경계를 맞춰야 한다.

공식 기준: [W3C WCAG 2.2 Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)은 AA의 24×24 CSS px 및 간격/인라인 등의 예외를 설명한다. 44px을 더 편한 내부 목표로 택할 수 있지만 AA의 보편적 최소치라고 부르면 안 된다. [W3C Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)은 200% 확대 시 내용/기능 손실 방지를 요구한다. 10px 이상이라는 검사만으로 이를 대체할 수 없다.

대안/부작용: 법/표준의 conformance와 제품 읽기 목표를 분리한다. 정보 밀도·기기·사용자 과업에 맞춰 예외를 허용하고 키보드·확대·대비·동적 알림을 실제 검사한다. 개별 예외가 무질서로 번지지 않게 이유와 사용자 결과를 기록한다.

수용 기준: 표준상 허용된 인라인 링크가 44px 미만이라는 이유만으로 WCAG FAIL로 분류되지 않으며, 큰 폰트여도 확대 시 잘리는 화면은 실패해야 한다. 분류: 표준과 제품 선택의 구별.

### E13 · P3 · native ESM은 타당한 기본값이지 영구적인 무빌드 원칙은 아니다

근거: ADR-0001:7~31, ADR-0002:7~12, CLAUDE.md:45, AGENTS.md:19,38. 5명용 정적 서비스에는 프레임워크 도입·전면 재작성보다 현재 pure domain/store/lifecycle을 이용하는 편이 비용이 낮다. 다만 도구 선택을 계속 deferred 상태로 두거나 “부분 패치만”을 절대화하면 반복 문제를 가장 싸게 해결할 선택을 막는다. ADR-0001의 src/legacy만 전역 호환 경계라는 규정과 현재 bootstrap 경계의 표현도 역할 기준으로 정리할 필요가 있다.

반례: 분해 후에도 수많은 파일의 요청/수동 캐시/배포 복제 때문에 반복 비용이 측정된다면 작은 bundler만 추가하는 것이 전면 재작성보다 단순할 수 있다. 반대로 타입 도구·프레임워크 도입이 실제 결함이나 사용자 대기 시간을 줄이지 않으면 무료 운영 복잡성만 늘린다. 1회용 abstraction 금지도 입출력 경계·보안 분리를 위한 작은 모듈까지 금지하는 뜻이어서는 안 된다.

대안/부작용: 현재 구조를 기본으로 유지하고 “관측된 성능/유지 비용 문제 + 한 작은 비교 실험”일 때 ADR 재검토를 열어 둔다. bundling·정적 타입·UI framework는 한 묶음으로 채택하지 않는다. 사용자 첫 표시/상호작용, 코드·배포 복구와 개발 시간의 실측 차이로 판단한다.

수용 기준: 동일 기능·동일 자료로 비교하며 버전·배포·rollback 복잡성을 포함한다. 뚜렷한 개선이 없으면 이행하지 않는다. 분류: 아키텍처 경험칙.

### E14 · P2 · 배치 한 번 검증은 경제적이지만 재검사 선택과 최종 identity를 다시 묶어야 한다

근거: post-edit-qa/SKILL.md:27~33, bug-fix/SKILL.md:30~31, WORKFLOW-GOVERNANCE.md:73, QA-PIPELINE-ARCHITECTURE.md:20~28. 일괄 실패 수집·내용 기반 PASS 재사용은 유지해야 한다. 그러나 “전체 수정 후 QA 한 번”을 원인 재현 금지로 읽거나, 실패 수정 뒤 exact failed gates만 재검사하고 새 영향 범위를 고려하지 않으면 다른 소비자의 회귀를 놓친다. Verify 다음 Record/version mutation 순서도 최종 증거가 어느 내용에 대한 것인지 명확해야 한다.

반례: 실패를 고치면서 공유 formatter를 바꾸면 직전 통과한 다른 화면도 입력이 달라진다. git merge·bump-version·cachebuster 변경 후에도 그 전 full 증거를 최종 배포 내용에 그대로 붙일 수 없다. 반대로 데이터와 무관한 문서 오타 때문에 전체 브라우저를 다시 돌릴 이유도 없다.

대안/부작용: 저렴한 재현/핵심 계약은 구현 중 허용하고 전체 QA는 배치한다. 수정 파일의 새 영향 설명을 확인해 실패 gate+새로 영향 받은 gate만 실행한다. 마지막 source/index 상태에 증거를 결속한다. 문서의 “static 뒤 browser” 순서는 현재 CI에서 둘이 preflight 뒤 병렬로 실행되는 사실(.github/workflows/ci.yml:60,105)과 일치시킨다.

수용 기준: 공유 helper 수정 반례가 소비자 검사를 추가로 선택하고, 무관 문서 수정은 불필요한 browser를 선택하지 않아야 한다. 기록 후 product 내용이 바뀌면 최종 identity 검사에서 드러나야 한다. 분류: QA/릴리스 경험칙.

### E15 · P3 · 규칙의 현행/역사 상태와 ID가 의미 추적에 충분히 명확하지 않다

근거: RULES.md:12는 32개 이외를 재발 추적용 이력이라고 하지만, 그 밖의 항목에도 v57.79 Rule 본문과 현재 commands가 인용하는 의무가 남는다. R230(:2134와 :2775)은 숫자 안전성과 뉴스 주기를 같은 ID로 지칭한다. R75는 원문 제목과 보강으로 나뉜다. R32 뒤 과거 P59(:2479~2480)의 fg ||18 예시는 현재 결측 분리와 정면으로 다를 수 있다.

반례: assertion이 R230만 인용하면 어떤 뜻을 보호하는지 ID만으로 알 수 없다. header-only R126의 “8개 프레임워크 인용 의무”를 현재 명령으로 읽으면 필요 없는 인용을 강제할 수 있지만, 전문이 없어 조건·예외를 확인할 수 없다. 제목을 보존하는 것과 현재 명령으로 적용하는 것은 별개다.

대안/부작용: 기존 governance-markers/catalog에 active/superseded/retired/history-only 상태와 정본 위치를 연결한다. 구문은 안정 ID+상태+후속 ID까지만 남기고 과거 명령은 실행 지시와 분리한다. 거대 새 정책 엔진이 아니라 현재 추적 자료의 필드 정리로 충분하다. ID 재번호는 기존 P/QA 추적을 깨뜨리므로 영구 alias를 보존한다.

수용 기준: 같은 ID의 다른 주제를 식별하고, header-only 이력을 새 코드 의무로 오인하지 않으며, 현재 명령에서 참조한 규칙은 실제 적용 가능한 정본으로 해석돼야 한다. 분류: 문서/추적 계약.

## 가장 작은 개정 순서

1. E01/E08/E15: 검사 수·명칭·ID가 실제 의미를 대체하는 부분부터 정리한다. 새 검사 플랫폼은 만들지 않는다.
2. E03/E04/E09/E14: 소유권·효과·이미 받은 승인·마지막 source identity를 명시해 잘못된 stop과 과도한 재검사를 줄인다.
3. R9/R156/R187/R189: event/fan-out/reload라는 수단 대신 필요한 데이터와 정해진 비용·현재성 결과를 계약화한다.
4. E10/E12: binary/글자수/44px 등 선호 수치를 품질 인증과 분리한다. 5명 앱에서 작은 실제 과업 관찰과 기존 게이트의 좋은 반례를 우선한다.
5. 대규모 프레임워크·타입·CI 교체는 현재 작업의 기본 결론이 아니다. 관측된 문제가 남을 때 한 작은 비교 실험으로 결정한다.
