# AIO Screener — Security & Privacy Audit
Scope: C:\projects\AIO (repo `ysnle/aio-screener`, PUBLIC). Read-only audit. Live checks limited to harmless GETs/OPTIONS against `https://ysnle.github.io/aio-screener/`, `https://aio-proxy.zmfhd007.workers.dev`, `https://aio-screener-data-plane.zmfhd007.workers.dev`. No secrets exfiltrated; any candidate secret is REDACTED to ≤4 chars.

## 1. Findings

### F1 — HIGH — Declared security headers (CSP, X-Frame-Options, Permissions-Policy, X-Content-Type-Options) are NOT actually served in production
**Evidence:** `_headers` (repo root, also copied verbatim into the Pages artifact by `.github/workflows/pages-deploy.yml`) declares a full header block including `Content-Security-Policy`, `X-Frame-Options: DENY`, `Permissions-Policy`, `X-Content-Type-Options: nosniff`. Live check:
```
curl -sI https://ysnle.github.io/aio-screener/
HTTP/1.1 200 OK
Server: GitHub.com
Access-Control-Allow-Origin: *
Strict-Transport-Security: max-age=31556952
... (no Content-Security-Policy, no X-Frame-Options, no Permissions-Policy, no X-Content-Type-Options)
```
GitHub Pages does not honor a `_headers` file (that syntax is Netlify/Cloudflare Pages convention); GitHub Pages only lets you set headers via Cloudflare/another CDN in front, which is not configured here. There is also no `<meta http-equiv="Content-Security-Policy">` fallback in `index.html` (verified: zero CSP-related `<meta>` tags; only `<meta name="referrer" content="strict-origin-when-cross-origin">` is present, which *does* work because meta-referrer is honored client-side).
Notably, the repo's own tooling already flagged this as unresolved: `architecture/security-sink-baseline.json` has `"liveHeadersStatus": "operator-observation-required"`, and `scripts/ci-csp-ratchet-check.mjs` only checks that the *text* of `_headers` contains a CSP string and the word live/observed/operator — it never fetches the live site to confirm the header is actually served. This audit's live curl resolves that open question: **it is not served.**
**Exploit scenario:** Any XSS (see F2) or third-party compromise (CDN, ad, browser extension) that would normally be blocked/limited by CSP is fully unmitigated; the site can also be framed by any origin (clickjacking — no `X-Frame-Options`/`frame-ancestors`), and MIME-sniffing protections are absent.
**Root cause:** Header policy authored for the wrong hosting model (Netlify/CF Pages `_headers` semantics applied to GitHub Pages).
**Remediation:** Put GitHub Pages behind Cloudflare (proxy DNS) and set the same header set at the Cloudflare edge (Transform Rules / Workers), or add an equivalent `<meta http-equiv="Content-Security-Policy">` in `index.html` for what meta can express (CSP script/style/img/connect directives — note `frame-ancestors` and `X-Frame-Options` cannot be set via meta, so framing protection needs a different technique, e.g. a small frame-busting script, until an edge proxy is added). Then change `ci-csp-ratchet-check.mjs` to assert against a live fetch of the deployed site, not the source file.

### F2 — MEDIUM — Public repo has GitHub secret scanning, push protection, and Dependabot security updates/alerts all disabled
**Evidence:** `gh api repos/ysnle/aio-screener` → `security_and_analysis`: `secret_scanning: disabled`, `secret_scanning_push_protection: disabled`, `dependabot_security_updates: disabled`, `secret_scanning_non_provider_patterns: disabled`. `gh api .../dependabot/alerts` → 403 "Dependabot alerts are disabled". `gh api .../secret-scanning/alerts` → 404 "disabled". These are free, one-click features for public repos.
**Exploit scenario:** A future commit that accidentally includes a real Anthropic/FMP/Cloudflare token (the app juggles ~13 provider credential types, per `_AIO_PROVIDER_REGISTRY` in `js/aio-core.js`) would not be auto-detected/blocked before or after push, on a repo the whole internet can already read.
**Remediation:** Enable secret scanning + push protection and Dependabot security updates in repo Settings → Code security. (Confirmed via API, not exploited.)

### F3 — MEDIUM — No branch protection on `main`
**Evidence:** `gh api repos/ysnle/aio-screener/branches/main/protection` returns a protection object with everything false/absent: `enforce_admins: false`, no `required_pull_request_reviews`, no `required_status_checks`. `rulesets` is `[]`.
**Exploit scenario:** Anyone with push access (or a compromised credential/token for a contributor) can push directly to `main` with no required review and no required CI status check gating the merge itself. Note: `pages-deploy.yml` does independently re-verify that a CI run succeeded for the exact SHA before deploying (a solid compensating control at the deploy layer — see "what's done well" below), so a bad push cannot skip CI's *existence*, but nothing stops a push that itself weakens/removes CI, or a human-approved bad change, from landing without review.
**Remediation:** Turn on branch protection requiring the `CI` workflow as a required status check and (even for a 1-person team) `enforce_admins`, to close the gap between "CI must have passed" (already enforced at deploy time) and "no one can bypass the requirement that CI runs at all."

### F4 — LOW/INFORMATIONAL (historical, already remediated) — `debug.log` (Chromium/agent debug noise) was tracked in git history for 3 commits
**Evidence:** `git log --oneline --all -- debug.log` → 3 commits (`b6b4e8de`, `b7e24ca2`, `a2473256`). Content sampled from the oldest commit is benign Chromium GPU logging (`cc\raster\one_copy_raster_buffer_provider.cc ... StagingBuffer's SharedImage failed`), not secrets or user data. Current working-tree `debug.log` (1MB) was also grepped for the standard key/token patterns — zero matches. `debug.log` is now in `.gitignore` and correctly excluded from the Pages artifact allowlist (`public-artifact-manifest.json` excludedFromPagesArtifact). No live secret exposure found, but the file (and its 3 historical blobs) remains permanently readable in the public repo's git history since history was never rewritten.
**Remediation:** No action required unless the team wants a cleaner history (`git filter-repo`/BFG) — low value given content is benign.

### F5 — LOW — Client-side "vault" encryption is real (not pure theater) but has caveats
**Evidence:** `js/aio-core.js:17176-17251` (`_AioVault`): PBKDF2-SHA256 (310,000 iterations current / 100,000 legacy) over a user PIN → AES-GCM-256 key; random 12-byte IV generated per `encrypt()` call (`crypto.getRandomValues`, no IV reuse observed); ciphertext format `aio_enc::` + base64(magic‖iv‖salt‖ciphertext). The derived key is held only in memory (`this._derivedKey`), never persisted — this is a legitimate design, not "key stored next to ciphertext."
Caveats:
- **PIN policy is weak**: minimum length enforced is 4 characters (`js/aio-core.js:19116`: `if (v1.length < 4)`), so a captured `aio_enc::...` blob + salt (salt is stored in plaintext localStorage under `aio_vault_salt`) is brute-forceable offline in a very small keyspace if 4 numeric digits are used, even at 310k PBKDF2 iterations (10,000 candidates × ~sub-second KDF cost each = trivial).
- **Encryption is opt-in and not the default**: portfolio data (`aio_portfolio_data`) and API keys are stored in plaintext localStorage unless the user has set a Vault PIN (`_pfVaultOptedOut()` / comment at `js/aio-workspace.js:214-217` explicitly documents that this used to be a bug — the UI claimed "AES-256 on save" while portfolio data actually took a completely separate plaintext path; this was fixed under an internal ticket "WO-1A/P661/R294/Codex P0-2" prior to this audit, per code comments — confirmed as *already fixed in code*, not currently reproducible from source, but the discrepancy is worth independently re-verifying live since the UI copy itself still overclaims — see F6).
- **Encryption does not protect against XSS**: any script that can execute in-page can simply call the same `_AioVault`/`_getApiKey()` functions the app itself uses (or read the `_keyRuntime` in-memory cache) to obtain plaintext keys — client-side encryption-at-rest only raises the bar against a *separate*, non-script-execution read path (e.g. someone copying the raw localStorage/IndexedDB off disk, or a browser-extension that only reads storage APIs, not one with content-script JS execution).
**Remediation:** Enforce a higher PIN/passphrase minimum (e.g., 8+ chars, reject pure numeric of <6 digits) and communicate to users that the Vault protects against local file/device exposure, not against a compromise of the app's own JS (which XSS defenses, not encryption, must cover).

### F6 — LOW — UI security copy overclaims relative to actual default behavior
**Evidence:** `js/aio-workspace.js:882`: `"데이터는 브라우저 localStorage에만 저장되며 서버로 전송되지 않습니다. PIN 설정 후 저장 시 AES-256 암호화."` — accurate about network transmission (true — see F7), but the "AES-256 after PIN" framing could be read by a lay user as "your data is always encrypted," when it is plaintext localStorage unless a PIN is explicitly set. This mirrors a documented past defect (F5) and is worth a one-line UI clarification (e.g., "PIN 설정 전에는 암호화되지 않습니다") given the Korean regulatory sensitivity of holding portfolio/holdings data.
**Remediation:** Tighten copy; consider defaulting new installs to Vault-on if there's no significant UX cost.

### F7 — INFORMATIONAL — Key transmission model is sound and matches documentation
**Evidence:** Provider keys are used directly from the browser to the named provider (e.g. `js/aio-pages.js:1510` FMP call with `?apikey=` query param sent straight to `financialmodelingprep.com`; `js/aio-chat.js` Claude calls go straight to `https://api.anthropic.com/v1/messages` with `x-api-key` header when a personal key is present — `_aioClaudeTarget()`, `js/aio-chat.js:1948-1961`). Only when no personal Claude key is configured does traffic route through the Cloudflare Worker's `/anthropic` route using an operator-held server-side secret (`ANTHROPIC_API_KEY` as a Worker secret, never in client code). This matches the app's "clientKeysStayBrowserLocal" claim for BYO keys. One structural weak point: FMP (and possibly other REST APIs) only support query-string auth, so the user's own FMP key appears in the request URL (visible in browser history/devtools/any shared HAR file, and in FMP's own server logs) — an inherent limitation of that provider's API design, not a bug in this app, but worth flagging as residual exposure.

### F8 — LOW — Non-constant-time secret comparison in data-plane worker's admin route
**Evidence:** `worker/data-plane.js:211-212`: `const supplied = request.headers.get('X-AIO-Cron-Token') || ''; if (!env?.AIO_CRON_SECRET || supplied !== env.AIO_CRON_SECRET) return ...401...`. Uses `!==` rather than a constant-time compare. Fails closed correctly if the secret env var is unset (good). Practically low risk: exploiting a timing side channel over the public internet against a Cloudflare Worker (which adds its own jitter) is very difficult, but it's a one-line fix (`crypto.subtle.timingSafeEqual`-equivalent / manual constant-time compare) for defense in depth.

### F9 — LOW — In-memory rate limiting in `cloudflare-worker-proxy.js` is per-isolate, not global
**Evidence:** `const rateLimitMap = new Map();` (`cloudflare-worker-proxy.js:249`) backs `RATE_LIMIT`/`ANTHROPIC_RATE_LIMIT`/`RELAY_RATE_LIMIT`. Cloudflare Workers can and do spin up multiple isolates for the same worker under load/geographic spread, each with its own `Map`, so a determined caller distributing requests can exceed the nominal per-minute limits by some multiple. The code's own comments are candid about this ("isolate 독립적인 실효 상한은 헤더에 적힌 Cloudflare WAF 레이트리밋 규칙뿐이다" — the only isolate-independent cap is an *external*, code-recommended Cloudflare WAF rate-limiting rule that must be configured out-of-band). **Importantly, the actual cost-control backstop for the expensive `/anthropic` and `/relay` routes is a Durable Object (`AIO_QUOTA_DO`) daily cap that IS global/consistent and fails closed (503) if not bound** — this is the real protection against runaway LLM cost from the shared key, and it is well designed. The in-memory map is only a soft, best-effort per-isolate throttle layered on top.
**Remediation:** Configure the documented Cloudflare WAF rate-limiting rule (300 req/min/IP) as the code comments already recommend; this is an infra/dashboard step, not a code change.

### F10 — Verified GOOD / not a finding — CORS on both Workers correctly rejects foreign origins
**Evidence (live check):**
```
curl -i -X OPTIONS https://aio-proxy.zmfhd007.workers.dev/ -H "Origin: https://evil.example.com" ...
→ Access-Control-Allow-Origin: https://ysnle.github.io   (NOT the requested evil origin)
```
Same result for the data-plane worker. Both workers reflect only their allowlisted production origin (`https://ysnle.github.io`) regardless of the `Origin` header sent, so a browser running on an attacker-controlled page cannot read cross-origin responses from either worker. The workers' own code comments correctly caveat that Origin-checking is a "minimum defense," not authentication, since non-browser clients (curl, server-side scripts) can freely spoof the `Origin` header — but that residual risk is already covered by the rate limits (F9) and the Durable-Object daily quota (fail-closed) for the expensive routes.

### F11 — Verified GOOD / not a finding — XSS sink hygiene
**Evidence:** 0 `eval(`, 0 `new Function(`, 0 `document.write(` across `js/*.js` and `index.html`. `eslint`-style raw counts: 390 `.innerHTML =`, 2 `.outerHTML`, 4 `insertAdjacentHTML` — but a DOMPurify-based sanitizer gateway exists and is used on the highest-risk paths: `window.safeHtml()` (`js/aio-core.js:140-160`, DOMPurify with an HTML-entity-escape fallback if DOMPurify fails to load), `_safeSetHTML()` (`:167`+), and `_aioSafeMD()` (`:1330`+, a second DOMPurify pass specifically for AI-chat markdown output, guarding against LLM-response-borne HTML/script injection). The custom lightweight markdown renderer `renderMarkdownLight()` (`js/aio-chat.js:1789-1889`) escapes `&`, `<`, `>` line-by-line *before* applying `**bold**`/`*italic*`/`` `code` `` regex transforms, and implements no `[text](url)` link syntax at all — so there is no markdown-link/`javascript:`-URI injection vector in AI chat rendering, a common LLM-chat-UI XSS pattern that is structurally absent here. Third-party CDN scripts (Chart.js, DOMPurify, lightweight-charts) are all pinned to exact versions and carry `integrity=` SRI hashes + `crossorigin="anonymous"`. No inline `on*=` event-handler attributes found in `index.html`. `scripts/ci-csp-ratchet-check.mjs` + `architecture/security-sink-baseline.json` enforce a ratchet ceiling (`innerHTMLAssignmentsMax: 450`, currently ~390-395, `unsafeEvalMax: 0`) in CI, preventing silent regression — a reasonable, if blunt, control (it counts occurrences; it does not verify each interpolation is escaped, so it's a regression-detector, not a sanitizer-completeness proof).
**Residual/unverified:** I did not exhaustively trace every one of the ~95 raw (non-gateway) `innerHTML =` assignments in `aio-core.js` to prove each interpolated value is escaped; spot checks (e.g. `js/aio-core.js:16626` using `escHtml()`) were consistent with escaping discipline, and no unescaped untrusted-data path (news headline, ticker memo, URL param) into an `innerHTML` sink was found in the time available, but this is not a 100%-of-lines guarantee.

### F12 — Verified GOOD / not a finding — Supply chain / CI hardening
**Evidence:** Every `uses:` action reference across all 9 workflow files is pinned to a full 40-character commit SHA (verified via regex across all `.github/workflows/*.yml` — zero non-SHA `uses:` refs found). `ci.yml` triggers on `pull_request` (not `pull_request_target`) with `permissions: contents: read` and references no `secrets.*`, so fork PRs cannot exfiltrate repository secrets through CI. No workflow in the repo uses `pull_request_target`. `pages-deploy.yml` re-validates (via GitHub API, not trusting the triggering event alone) that the exact SHA it's about to deploy was the one CI actually tested and passed — a strong, actively-hardened deploy gate (the workflow's own comments describe a prior incident, "R606," where a bot-dispatched CI run had no attestation consumer, and the fix). `dependabot.yml` exists for version-update PRs (separate from the disabled security-alert feature in F2). `contents: write` is scoped only to the two data-refresh workflows that legitimately need to commit fetched data back to the repo.

### F13 — Verified GOOD / not a finding — Service worker
**Evidence:** `sw.js` uses network-first (not cache-first/stale-while-revalidate) for the app shell (`fetch(request, {cache:'no-store'})...catch → cache fallback`), so users get fresh code whenever online and the SW cannot indefinitely serve stale/compromised JS — it only serves cache when the network fetch itself fails (offline fallback). `isSensitiveUrl()` gating excludes sensitive/data-bearing URLs from being persisted into either cache (`SHELL_CACHE`/`DATA_CACHE`); code comments show the team already found and fixed one asymmetry bug here (`./js/aio-core.js?token=…`-shaped URLs previously slipping into `SHELL_CACHE` because the shell-cache path only checked pathname, not the sensitive-URL check the data-cache path used). Data cache entries carry TTL headers and an eviction/FIFO cap (500 keys). No evidence of cache-key confusion or scope escalation beyond the registered `/aio-screener/` scope.

### F14 — Privacy/data-handling summary (informational, not scored)
- Portfolio holdings (`aio_portfolio_data`) and all provider API keys live only in the browser's `localStorage`/`sessionStorage` (public mode uses `sessionStorage`) — confirmed no code path uploads portfolio contents to any Worker or third party; `savePortfolioData()`/`getPortfolioData()` (`js/aio-workspace.js:226-268`) touch only `localStorage`/the Vault.
- The GitHub Actions "data backend" (`public-data/*.json`) is server-fetched *market* data (quotes, macro, F&G), not user data — no user PII flows into that pipeline.
- No analytics/telemetry SDK (GA, Mixpanel, Sentry, etc.) was found in `index.html` or `js/*.js` (unverified exhaustively, but no `<script>` tag or `fetch()` to a known analytics domain was found in the greps run).
- `public-artifact-manifest.json` explicitly documents an allowlist model for what the Pages artifact contains, and separately documents what is excluded (bulk 13F/holdings ledgers, `.claude/`, `.codex/`, `scripts/`, `debug.log`, PDFs, `.py` files) — this is a good, explicit contract, and `pages-deploy.yml`'s staging step matches it. However, note that the *source repo itself* (not the Pages artifact) is fully public, so anything excluded from Pages (agent configs, internal audit docs, `_context/` postmortems, `_artifacts/`) is still world-readable on GitHub — this is a visibility/business-confidentiality consideration, not a technical vuln, but worth the operator's awareness for a repo carrying investment-research methodology and internal QA findings.
- Korean 유사투자자문업(quasi-investment-advisory) angle: not independently assessed for legal compliance (outside audit scope/expertise); flagging only that an app providing "AI 교육·리서치 보조" + portfolio tooling to Korean users should have a clear, prominent disclaimer that it does not provide licensed investment advice — worth a legal/compliance review by the operator, not something this security audit can certify.

## 2. How I would design security for this app (threat model + comparison)

**Actual assets to protect, roughly by value:**
1. The ~5 users' personal API keys (Anthropic/FMP/Finnhub/etc.) — moderate value (mostly rate-limited free/cheap tiers, but Anthropic keys can incur real $ cost).
2. The shared/operator Anthropic key behind the Worker — the highest-value asset; a leak or bypass turns into an open, cost-bearing LLM relay for the whole internet.
3. Users' portfolio holdings — sensitive but low-blast-radius (financial privacy, not credentials); no direct monetary exploit from disclosure alone.
4. Repo/CI integrity — a compromise here (bad commit reaching Pages, or a workflow secret exfiltrated) affects every user simultaneously (supply-chain blast radius), and is the most consequential failure mode for a small team with big radius (public site, shared trust).

**Threat model for "public static site + BYO keys + shared LLM relay":**
- Attacker classes: (a) drive-by/XSS attacker who gets script execution in a victim's browser session, (b) network/off-path attacker abusing the shared Worker relay for free LLM usage or cost-DoS, (c) supply-chain attacker (compromised CDN dependency, compromised contributor credential, malicious PR), (d) opportunistic scraper hitting exposed GitHub history/repo for secrets.
- Given that, the priority order should be: **(1) supply chain + CI integrity, (2) shared-relay abuse/cost control, (3) XSS, (4) at-rest encryption of local data.** This project's actual investment (judging by code comments/version history full of "P###/WO-#" hardening tickets) already matches that order reasonably well — CI SHA-pinning, deploy-time re-attestation, and the Durable-Object fail-closed daily cap are all sophisticated, above-average controls for a project this size. The gaps found (F1 headers, F2 repo security features, F3 branch protection) are comparatively *cheap, high-leverage, unimplemented settings/config*, not architecture failures — which is the encouraging framing: fixing F1–F3 does not require redesigning anything.
- Where I'd differ from the current approach: client-side "vault" encryption of BYO keys is defensible as a nice-to-have (raises the bar against a narrow class of local-file-disclosure threats) but the team should be explicit internally and in the UI that it is *not* an XSS mitigation — the mitigation for XSS is sink hygiene + CSP, and CSP is the one layer that turned out not to be live (F1). I would prioritize actually landing CSP (even a `meta`-tag partial version restricting `script-src`/`connect-src` while X-Frame-Options is unavailable via meta) over further hardening the vault, since CSP is the control that limits blast radius *if* an innerHTML sink is ever missed, whereas vault hardening only helps a threat model (local device/file access) that is arguably lower priority for 5 trusted users than "some future contributor introduces one bad interpolation."

**Prioritized remediation plan:**
1. (Cheap, high leverage) Enable GitHub secret scanning + push protection + Dependabot security updates (F2). Add branch protection requiring the CI status check on `main` (F3).
2. (Medium effort, high leverage) Land real security headers: put Pages behind Cloudflare (or another edge that reads `_headers`), or at minimum ship a CSP `<meta>` tag in `index.html`; fix `ci-csp-ratchet-check.mjs` to assert against the live URL, not just the source file text (F1).
3. (Low effort) Raise minimum Vault PIN length/complexity; adjust UI copy to stop implying always-on encryption (F5, F6).
4. (Low effort, optional hardening) Constant-time compare for the cron-token check (F8); confirm the recommended Cloudflare WAF rate-limit rule is actually configured (F9 — this is a dashboard setting the code already tells the operator to add).
5. (No code change, awareness only) Treat the public GitHub repo's `_context/`, `_artifacts/`, and agent-config directories as public even though they're excluded from the Pages artifact (F14); get a compliance read on the 유사투자자문 disclaimer language.

All items above are configuration/settings changes or small, targeted code edits — nothing found here requires an architectural rewrite.
