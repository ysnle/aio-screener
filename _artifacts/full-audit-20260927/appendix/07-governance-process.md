A single day (09-25) produced 50 "postmortems." Git log confirms mega-batch commits: `feat: handoff remainder batches + E2-C6 QA identity (P1205~P1265, v56.15→v56.52)` and `chore: land accumulated local work — P1205~P1259 (v56.15→v56.49)` — i.e., dozens of P numbers and ~35 version bumps landed in one or two commits. This is not "one incident → one postmortem"; it is an agent batch-generating ledger entries to satisfy R3 ("bug fix requires a P entry") after the fact, for what reads as ordinary iterative refactor work (e.g., P1278–P1282, five entries in one session, all about the same portfolio-reader refactor). **The ledger's unit of account has drifted from "distinct bug" to "thing an agent touched."**

### 1b. Rule count vastly exceeds anyone's ability to honor them
571 `## R` headings, R1–R632 (gaps = deliberate retirements, per `ci-ledger-integrity-check.mjs`'s own justification). AGENTS.md tells agents not to load RULES.md in full — only grep by keyword. That is an implicit admission that the ruleset is unusable as a corpus: it functions as a **search index of settled disputes**, not as a set of principles a human or model could internalize. Compare to the explicit design intent in root CLAUDE.md itself: "절대 규칙 (R1~R3만 — 나머지는 RULES.md)" — the maintainers already concluded only 3–4 rules are load-bearing enough to keep in the primary instruction file; everything else is reference material consulted reactively, which is a reasonable coping mechanism but does not change that 571 rules were still written.

### 1c. QA-CHECKLIST has 731 distinct IDs across 95 different naming schemes
`QA-01`, `QA-AI-06`, `QA-A11Y-20260830-01`, `QA-AIAUTH1`, `QA-CRED-05`, `QA-SIG-27`, `QA-THM-CLEANUP`, `QA-GLOSSARY-SWEEP`, `QA-FX-REFRESH`… 95 distinct prefix families with inconsistent delimiter/numbering conventions (some hyphen-numbered, some concatenated, some date-stamped, some free-text slugs). The "200 open QA IDs" cited in the task brief is a small fraction of the 731 total — meaning ~530 are presumably closed/historical, another large compacted archive similar to BUG-POSTMORTEM.

### 1d. Repeat-bug-class table: evidence the ledger *is* catching real recurring classes, but also evidence gates give false confidence
`_context/BUG-POSTMORTEM.md:4221`, "반복 버그 클래스 (재발 추적 — R25 승격 원장)" lists 14 named recurring bug classes with their representative P-numbers, e.g.:
- "이중 표면·그림자 구현 드리프트" (duplicate/shadow implementation drift): P276, P492, P605, P606, P625, P713, P719, P741, P745 — **9 recurrences of the same class**
- "생산자-소비자 파이프 단절" (producer built, consumer never wired): P239, P548, P652, P664, P721, P724, P743 — **7 recurrences**
- "fail-closed 위반": P635, P649, P706, P712, P713, P717, P718 — **7 recurrences**
- "관측 시점 리터럴 부패" (hardcoded observation-time literals rotting): P604, P627, P713, P715, P720, P722 — **6 recurrences**

This is a genuinely useful piece of the system — it is the one place where the volume pays for itself, because it turns "we keep hitting the same bug shape" into a countable, named fact. But **P740 is a self-documented case where the anti-pattern the gate was built to catch (진척 인플레이션 — "declaring architecture-migration progress without real ownership transfer") recurred in the very next batch after the rule (R352) and its gate were created**: "R352가 막으려던 패턴이 R352 제정 바로 다음 배치에서 재발했다" (the pattern R352 was meant to block recurred in the batch immediately following R352's creation). The postmortem for P740 explicitly names the mechanism: the enforcing gates (`ci-retirement-contract.mjs`, `ci-operations-status-check.mjs`) were checking a hand-written literal ownership array against itself, not against actual code — i.e. a tautological ("self-proving") gate structure, passing "17/17 native" while a hard-coded array said so, while three separate handoff documents simultaneously claimed three different, mutually contradictory ownership counts (17/0, 4/13, 0/17) for the same migration. This is direct, first-party evidence for the "false confidence" risk named in the task brief — the org's own postmortem literally used the term for the phenomenon and gave it a name so it could recur again.

### 1e. Token/cost burden on agents
Combined size of the four ledgers agents are told to consult (BUG-POSTMORTEM 1.19MB + RULES 412KB + QA-CHECKLIST 349KB + CHANGELOG 539KB) ≈ **2.5MB of raw governance text**, before touching the 74 `_context/` docs (4.7MB total) or 129 CI gate scripts (most of `scripts/`'s 3.4MB). AGENTS.md's own mitigation — "don't load these in full, grep by keyword" — is the correct move, but it means the investment in writing 571 rules and 1,282 postmortems has a *retrieval* cost proportional to corpus size even when reading only a slice (grep over a 1.19MB file still costs a tool call and burns tokens on the matched context), and a **maintenance cost**: `ci-ledger-integrity-check.mjs` and `ci-assertion-trace-check.mjs` exist purely to keep the ledgers internally consistent (R-number gap tracking, ledger-id citations on new assertions) — governance overhead spent on governance, not on the product.

### 1f. Repo bloat
`.git` is 1.7GB for a dependency-free static HTML/JS app. The four ledger files alone have been rewritten wholesale hundreds of times (291+215+182+450 = 1,138 commits touching just those four files, each commit storing a new full blob of a multi-hundred-KB file since git has no diff-aware compression for text until repacked). This is a direct, measurable cost of the ledger-as-single-giant-markdown-file design.

**Rough ratio from the sample and full-repo `grep`:** of 129 `ci-*.mjs` files, 24 (~19%) actually drive a headless/real browser (Playwright/Chromium) and constitute genuine behavior tests (category a). At least 6 of the sampled files are pure category-(d) self-referential meta-gates (checking ledgers/docs/other-generated-docs against each other), and grep confirms 22/129 (~17%) read `_context/*` documents directly as part of their pass/fail logic — i.e., roughly one gate in six has app-shippability coupled to prose-document content, exactly the brittleness the task hypothesized. Extrapolating the sampled ratio (8 of 20, 40%, showed no direct behavioral assertion — pure schema/regex/meta), a plausible full-repo estimate is that **well under half of the 129 gates test actual runtime behavior**; the rest test that documents/generated-artifacts/other-gates are self-consistent, or that specific string patterns exist/don't exist in source.

**Direct, first-party evidence these were not coherently reconciled while active**: P740's postmortem (quoted above, §1d) states plainly that *three* of these documents — the 07-18 handoff, the 07-19 execution plan, and `INDEX.md` — simultaneously asserted three different, mutually incompatible native/legacy route-ownership counts (17/0 vs 4/13 vs 0/17) for the same migration, and that this was only caught when a human explicitly pushed back ("사용자가... 재지적") on the disconnect between rising file/gate counts and near-zero legacy code deletion. The remediation applied strikethrough-and-correction annotations rather than deleting the wrong numbers, so the contradictory claims are still physically present in the files today (not verified in this pass — flagged as **unverified**, would require reading the specific line ranges in all three docs).

None of the sampled dated docs carry a machine-readable "superseded-by" or "status: closed" pointer to a successor doc — closure is asserted in prose (if at all) rather than structurally, so a new agent opening `_context/` alphabetically has no way to know that (for example) `ARCHITECTURE-REBUILD-HANDOFF-2026-07-18.md` was substantially superseded by the -07-19 execution plan and remediation handoff without reading all three and diffing them by hand. `CONTEXT-CATALOG.json` and `INDEX.md` exist specifically to solve this routing problem, which is itself telling: the volume of historical documents grew large enough to need its own index-of-indexes, and the index is itself a 24KB generated JSON file kept in sync by yet another gate (`ci-knowledge-lint-check.mjs`).

## 4. Agent tooling

- `.claude/`: 4 agents, 19 skill dirs (mirrored 1:1 in `.agents/skills` for Codex — genuine duplication, both trees have `autoresearch`, `bug-fix`, `data-refresh`, `integrate`, `knowledge-lint`, `post-edit-qa`, `_shared`), 9 commands, 0 dedicated hooks directory (hooks are wired through `.claude/settings.json` calling a single `scripts/agent-hook.mjs`).
- `.codex/agents/` holds 4 separate `.toml` agent personas (accessibility-auditor, code-reviewer, performance-analyzer, qa-auditor) not mirrored in `.claude/agents` — asymmetric duplication, not full 1:1.
- `.commandcode/` is a third, apparently unrelated tool config (`taste.md`) — a third agent-tooling surface alongside `.claude`/`.codex`/`.agents`.
- **Hooks are safety-reasonable**: `scripts/agent-hook.mjs` (97 lines) is a small, readable PreToolUse/PostToolUse dispatcher that denies `git reset --hard`, force-push, and broad recursive deletes via regex, and is explicitly advisory-only elsewhere (per root CLAUDE.md: "자동 커밋 훅을 추가하지 않는다. 훅은 파괴 명령 차단과 advisory 검증만 수행한다" — hooks do destructive-command blocking and advisory checks only). This is a genuinely well-scoped, low-risk piece of the system.
- `.claude/settings.local.json` grants broad standing Bash allowlist including `git add`, `git commit`, `git push`, `git checkout`, `git merge`, `git pull` with wildcard args, plus `python`/`python3`/`node` unrestricted, and a long list of pre-approved outbound `WebFetch` domains (Yahoo Finance, FRED, Naver, WSJ, Cboe, etc.). This is broad autonomy for a single-owner project; reasonable given the stated "no auto-commit/push without explicit request" *policy* (which lives in prose, not in the permission system — the permission system technically allows an agent to push whenever it decides to, and only AGENTS.md prose asks it not to).
- **Workflow proportionality**: AGENTS.md prescribes a mandatory preflight (git status + qa-runner session-start baseline), a task-routing table across 6 skills, and a closeout of 10 mandatory gate commands (9 `ci-*.mjs` + `git diff --check`) *at minimum*, "plus code/data/browser gates selected by the touched surface." For a single-owner, ~5-concurrent-user hobby-scale product, this is roughly the CI discipline of a small commercial engineering team's release process, not a side project's. It is not obviously wrong — the postmortems show real regressions this discipline caught — but it is disproportionate to the team size (1 human + AI agents) driving it, and the 1,138 ledger-touching commits and 50-P-entries-in-a-day pattern above suggest the process consumes more of each session than a smaller, sharper set of checks would.

## 5. Versioning process

- v38.9 (2026-04-02) → v56.55 (2026-09-27): 178 days, 316 distinct version headers in CHANGELOG.md ≈ 1.8 version bumps/day average, but heavily clustered — e.g. the "P1205~P1265" commit alone spans v56.15→v56.52 (37 patch versions) in what reads like a single working session compacted into two commits.
- R1 requires `node scripts/bump-version.mjs <version>` to sync title, badge, `APP_VERSION`, `version.json`, `sw.js` `SW_VERSION`, root/context docs, `CHANGELOG.md`, and JS cachebusters — at least 7 distinct file locations for every single-digit patch bump. This conflates **version number** with **unit of work tracked** — a version bump here is closer to a commit-message tag than a release, since dozens can land in one working session, but each still requires touching 7 surfaces.
- No evidence of semantic versioning discipline (major/minor/patch tied to compatibility or scope) — version is monotonically increasing but the task brief and CLAUDE.md both describe it as tracking *progress*, not compatibility or release readiness. `architecture/public-readiness.json` (current appRevision v56.55) still gates "PUBLIC_BETA" promotion on unmet criteria (`route-soak: PENDING_LOCAL_GATE`, `boot-performance: REMEASURE_REQUIRED`, `accessibility-manual: OPERATOR_REQUIRED`, `thirty-day-slo: OPERATOR_REQUIRED`, `live-revision: OPERATOR_REQUIRED` — the live deployed revision is confirmed to be v56.33, i.e. **already 22 patch versions behind local HEAD**, undeployed). So "56 versions in" the product has still not cleared its own self-defined beta bar, and the local/live gap itself is large and growing.

## 7. Product charter coherence / scope

`architecture/product-charter.json` (schemaVersion `aio-product-charter.v1`) defines: productIdentity with `executionCapability: NONE`, `stage: RESEARCH_BETA_CONDITIONAL`; 6 allowedOutcomes; 6 explicit nonGoals (no trade execution, no general chatbot, no full CMS/backtest/portfolio-accounting platform); 6 experience principles; a 4-tier `evidencePolicy`; **7 named "trust planes"** (public-shell, durable-current-data, fast-market-reference, research-corpus, personal-vault, ai-synthesis, operations-evidence) each with `contains`/`mustNotContain`; 8 architecture principles; a 14-row `auditCoverage` table (each domain marked AUDITED with a distinct implementationStatus enum value); a `deploymentBoundary`; an `aiBoundary`; and 7 `promotionGates` gating a `RESEARCH_BETA_CONDITIONAL → PUBLIC_BETA` transition.

This is a **formally complete, internally consistent, enterprise-grade product-governance document** — better structured than most seed-stage startups' actual charters. It is also wildly disproportionate to a static GitHub Pages site with 5 known users run by one person. The nonGoals list (no execution capability, no general chatbot) is sensible and matches what's built (screener + AI chat is scoped to "evidence-bound analyst," not autonomous trading). Scope did visibly grow over the observed history well beyond "screener": the product now includes an AI chat, a Masters 13F portfolio-holdings tracker, a "Market Principles" knowledge atlas with curriculum/taxonomy specs, a portfolio vault, macro/FX/credit dashboards, and ~20 routes per the task brief — consistent with the ~30 dated spec/handoff docs seen in `_context/` (AI-ERA-*, MARKET-PRINCIPLES-*, MASTERS-PORTFOLIO-13F-*, SCREENER-OPEN-SOURCE-BENCHMARK-*). The charter itself does not contradict what was built; rather, the charter's *formalism* — SLO windows, 30-day operations windows, promotion gates, provider-rights review, a not-yet-built "future bulk store" for retention-managed 13F/PIT data — describes a company preparing for a public launch with compliance exposure, while `public-readiness.json` confirms the product is still `BLOCKED_UNTIL_OPERATOR_CRITERIA_CLOSE` on criteria (accessibility manual review, 30-day SLO, live-revision confirmation) that a 5-user hobby tool run by its own operator does not obviously need before continuing to serve those 5 users.

# Findings

**Critical**

- **C1. Self-referential/meta gates have caused at least one real deploy-pipeline outage and one long-lived false-"PASS."** `ci-workspace-contract-check.mjs` contains an embedded postmortem (P1160) describing exactly this: an earlier version of the gate pinned a data-derived value into a generated doc and then broke Pages deployment on every scheduled data refresh. Separately, P740 documents an entire earlier generation of ownership-tracking gates (`ci-retirement-contract.mjs`, `ci-operations-status-check.mjs`) that verified a hand-written literal array against itself rather than real code, reporting "17/17 native" while three governance documents simultaneously claimed three different, contradictory ownership counts. Evidence: `_context/BUG-POSTMORTEM.md` P740, `scripts/ci-workspace-contract-check.mjs` (P1160 comment).
- **C2. Ledger growth rate is accelerating and its unit of account has drifted from "distinct incident" to "thing touched in a session."** 50 P-entries were created in a single day (2026-09-25); the "P1205~P1265" commit landed ~35 versions and dozens of P-numbers in what reads as one working session. This inflates the very corpus that R25/R3 rely on to detect *real* recurrence (§1a, §1d), diluting the signal the repeat-class table depends on.

**High**

- **H1. Roughly one CI gate in six (22/129 sampled by direct `_context/` file reads) couples pass/fail to specific prose strings in documentation**, and the project's own root instructions warn agents not to delete the magic strings those gates grep for (e.g. `ci-semantic-review-check.mjs` hard-requires the literal heading `## v50.89` to exist in CHANGELOG.md forever). This is brittle by construction and inverts the normal doc/code relationship: documentation text becomes load-bearing for shippability.
- **H2. Under half of sampled CI gates test runtime behavior; the rest test document/generated-artifact self-consistency or source-text regex patterns.** Of 20 gates sampled across categories, 6 were pure category-(d) self-referential meta-gates, several more were category-(c) regex-on-source, and only ~9–10 drove real assertions against running code or a real browser. 24/129 (19%) launch a real Chromium instance; that is the strongest, most trustworthy subset, but it's a minority of the total gate count.
- **H3. Documentation sprawl includes at least one first-party-documented case of three concurrently-active handoff/plan documents making mutually contradictory factual claims** (route-ownership counts 17/0 vs 4/13 vs 0/17) about the same in-flight migration, caught only by a human's manual pushback rather than by any of the 129 automated gates. No structural (machine-checkable) "superseded" marking exists between overlapping architecture docs (ARCHITECTURE-REBUILD-HANDOFF / -EXECUTION-PLAN / -REMEDIATION-HANDOFF / STRUCTURAL-REMEDIATION-MASTERPLAN).
- **H4. Repo bloat: 1.7GB `.git` for a static, dependency-free web app**, substantially driven by four ledger files being rewritten as whole-file blobs across 1,138+ commits total.
- **H5. Live deployment lags local HEAD by 22 patch versions** (live v56.33 vs local v56.55 at audit time per `public-readiness.json`'s own "live-revision" criterion), and the product's own promotion gate (`PUBLIC_BETA`) has been unmet since at least the point that document was authored, with several criteria marked `OPERATOR_REQUIRED`/`REMEASURE_REQUIRED` that depend on a human operator action that evidently has not happened. The governance apparatus produces a correct, honest status (this is arguably a success of the fail-closed design) but the gap between "56 versions of gated progress" and "operator hasn't confirmed live state matches" is itself a symptom of process consuming cycles that could have closed the actual gap.

**Medium**

- **M1. Tooling triplication**: `.claude/`, `.agents/` (Codex mirror), `.codex/`, and `.commandcode/` are four overlapping agent-configuration surfaces; `.claude/skills` and `.agents/skills` are near-exact duplicates (same 7 skill names) that must be kept in sync by hand or by `sync-agent-skills.mjs`.

# Root causes

1. **Every safety mechanism is opt-in prose, enforced by an agent choosing to follow AGENTS.md/CLAUDE.md, rather than by tooling that makes the unsafe path unavailable.** The permission system allows `git push --force`-adjacent operations to be *attempted* (the hook blocks the specific dangerous regex patterns, not a broader default-deny); the "no ledger bloat" instinct is asserted in CLAUDE.md prose ("대형 RULES/QA/BUG/KNOWLEDGE 원장은 관련 용어만 검색") rather than structurally prevented by, e.g., splitting the ledger into per-quarter files that are naturally bounded in size.
2. **The project conflated "make agents accountable for regressions" with "make agents write a ledger entry for every touched thing."** R3's "bug fix requires a new P entry" is a reasonable rule for genuine defects; applied by an agent under a "complete = fully verified" self-image, it produces 50 entries in a day for what is largely one refactor session's worth of internally-discovered issues, most caught by the same session's own gates rather than by a user or later regression.
3. **Meta-gates (checking gates/docs/generated-artifacts against each other) were added reactively, each time a specific drift was caught once, without a design principle limiting how many diagnostic self-checks a project this size should carry.** Each individual meta-gate has a legible, well-reasoned origin story in its own comments (this is a real strength — the code explains itself unusually well) but the sum is a governance layer whose own internal consistency now requires dedicated maintenance (ci-ledger-integrity-check, ci-assertion-trace-check, ci-doc-currency-check, ci-knowledge-lint-check, ci-workspace-contract-check, ci-six-doc-coverage-check — 6 of ~20 sampled gates exist to protect the other governance artifacts, not the product).
4. **No forcing function ever retires a stale plan document or ledger entry.** Nothing structurally marks a HANDOFF doc "closed" (no `status: superseded` field enforced by a gate the way ledger IDs are enforced); closure lives in prose annotations layered onto files that are never deleted, so the sprawl only grows monotonically, matching the version-number's own monotonic-only growth pattern.
5. **The product's ambition (charter-level rigor: trust planes, evidence policy, SLOs) outran the product's actual deployment/usage reality (5 users, one operator, live version 22 patches behind HEAD).** The charter is not wrong, but writing and maintaining it consumed effort that a 5-user tool arguably didn't need yet — a "grow into it" charter would have cost less and could have been expanded once real usage justified it.

# Impact

- **Agent session cost**: every session pays a tax reading/grepping across ~2.5MB of ledger text plus 74 `_context/` docs before or during work, per AGENTS.md's own prescribed preflight — a real, recurring token/latency cost that the "search don't load" mitigation only partially offsets.
- **False confidence risk realized twice on record** (P740, P1160) — both caught eventually, but only after already causing a deploy break (P1160) or shipping a visibly broken user-facing table for some period (P740's screener 22-col-vs-5-col collision).
- **Maintenance burden compounds**: 129 gates, many depending on specific document strings, mean routine doc cleanup (compressing CHANGELOG, archiving old handoffs) is itself a CI-risk activity requiring careful auditing of which magic strings are load-bearing — this is explicitly called out as a known risk in root CLAUDE.md, meaning the maintainers are aware and are manually compensating for it every time, rather than the system being safe by construction.
- **Net signal-to-noise in the ledgers is dropping** as entry-creation accelerates without a corresponding filter for "is this actually a new bug class or the day's incidental refactor byproduct" — the exact mechanism (repeat-class tracking) meant to make the volume worthwhile depends on postmortems being about genuinely distinct incidents, which the September acceleration undermines.
- **On the positive side**: the repeat-bug-class table (§1d) is a real, working example of the ledger paying for itself — 9 recurrences of "shadow implementation drift" caught and eventually gated (`AG-DOM-WRITER`) is a legitimate win that ad hoc bug-fixing without any ledger would likely have missed. The behavior-test subset of gates (Playwright-driven, ~19% of the total) and the hook safety design are also genuinely well-built and worth preserving in any redesign.

# How I would run development for this project instead

**Design target**: keep the things that measurably worked (repeat-class detection, real browser tests, fail-closed data handling, honest "OPERATOR_REQUIRED" status reporting) while cutting the volume of prose governance to something a human and an agent can both hold in working memory, and replacing self-referential meta-gates with structural guarantees that don't need a gate to check them.

### 1. Replace the four giant ledgers with:
- **~15–20 Architecture Decision Records (ADRs)**, one file each, ~1 page, covering only decisions that actually constrain future choices (e.g. "route ownership transfers require deleting the legacy renderer in the same PR," "evidence must carry sourceKind/observedAt/allowedUse," "no HYG-dollar-threshold credit judgments — use FRED HY OAS"). Immutable once written; superseding one gets a new ADR that references the old number, git history is the audit trail, not a hand-edited "compacted" line.
- **One short living architecture doc** (~150–300 lines) — replaces CODE-MAP.md/CURRENT-STATE.md/INDEX.md/CONTEXT-CATALOG.json's routing function with a single hand-maintained page of "where things live," regenerated/verified by one lightweight script, not five.
- **A distilled "lessons" doc, ~20–40 entries**, one paragraph each, produced by *reading the 1,282 P-entries once* and keeping only the ones that represent a genuinely distinct recurring failure mode (the 14-row repeat-class table already does 90% of this triage — promote exactly those 14 classes, plus any P-entry with 3+ recurrences not yet in that table, and drop the rest). Each lesson becomes one executable regression test (not a markdown paragraph) wherever feasible — e.g. "no HYG-dollar credit threshold" becomes a `grep`-free, AST/semantic test in the real gate that already type-checks credit logic, not a paragraph an agent has to remember to re-read.
- **GitHub Issues (or a Project board)** as the unit of open work, replacing QA-CHECKLIST's 731 free-text IDs with real issues that have state (open/closed), labels, and linked PRs — closure is structural (issue closed by a merged PR), not a manually-updated status field in a markdown table.

### 2. Replace ~129 `ci-*.mjs` gates with a real test pyramid:
- **Keep** the ~24 Playwright-driven behavior gates (they're the most trustworthy layer) but consolidate overlapping ones (e.g. multiple per-route `*-browser-check.mjs` files could likely share one parametrized runner).
- **Keep** unit tests like `ci-esm-core-unit-check.mjs`'s actual assertions, but move them into a real test runner (`node --test`, or vitest) instead of a hand-rolled `check()`/`errors[]` pattern duplicated ~130 times — this alone would cut meaningful boilerplate and make failures report consistently.
- **Delete** the self-referential meta-gates (`ci-doc-currency-check`, `ci-ledger-integrity-check`, `ci-assertion-trace-check`, `ci-six-doc-coverage-check`, `ci-workspace-contract-check`, `ci-knowledge-lint-check`) as CI gates. If the underlying generated-doc-drift problem still matters once the ledgers are radically smaller, make the doc *generated only* (no hand-editable copy to drift from) rather than gating on "hand copy == generated copy."
- **Replace** doc-string-coupled gates (`ci-semantic-review-check.mjs`'s literal `## v50.89` grep, and similar) with gates that check a durable *structural* fact (e.g. "a `semanticReview: true` field exists on the relevant JSON record") instead of a specific heading string that becomes a landmine for future doc cleanup.
- **Target**: cut 129 gates to something like 30–40, organized as unit (fast, no browser) → integration (real browser, ~15-20 min) → a small number of release-gating checks, with a documented **≤10-minute** PR-blocking tier and the heavier browser matrix reserved for pre-deploy only (this project already separates "browser" into its own CI stage — the target is shrinking that stage's scope and gate count, not inventing the separation).

### 3. One agent instruction file, ≤150 lines
Merge CLAUDE.md + AGENTS.md (they currently duplicate the "read CURRENT-STATE once, don't load ledgers in full" guidance almost verbatim) into a single file: identity/stack (5 lines), the 3-4 rules that are actually load-bearing (R1-style version sync, fail-closed evidence, no auto-deploy), where to find more detail if truly needed (ADRs + living arch doc), and the minimal closeout check. Drop the 10-command mandatory closeout to whatever the new ≤10-minute test tier requires — if it's well-designed, "run the test suite" replaces a 10-item manual list.

### 4. Versioning: adopt Conventional Commits + semantic-release (or a much lighter manual scheme)
Let commit messages (`fix:`, `feat:`, `feat!:`) drive an automatically-computed semver, generate the changelog from commit history instead of hand-authoring 539KB of prose, and stop treating "version number" as a progress-tracking device — 37 patch bumps in one working session is a sign the number is being used to mean "commit," which conventional commits + auto-changelog would fix directly (every commit still gets a durable, searchable record; it just isn't a hand-maintained CHANGELOG.md entry and doesn't require touching 7 files by convention).

### 5. Repo hygiene
Move `AIO_Screener_API_Setup_Guide.pdf`, `aio_api_setup_guide.py`, `_patch_pm.py` into a `tools/`/`docs/` subfolder (or a separate repo if they're genuinely unrelated to the deployed app); delete or gitignore `debug.log`, `_backup/`, `_archive/`, `_codex-qa-cache-runtime-dup/`; once ADRs replace the JSON allowlist's *reason* for existing (the allowlist exists partly because non-web files sit at root), the allowlist file itself can shrink to a genuine "what's public" declaration rather than also doing cleanup duty.

### 6. Product charter: keep the nonGoals, shrink the ceremony
The 6 `nonGoals` and `executionCapability: NONE` line are valuable and cheap — keep them verbatim as one of the ADRs. Retire the 7-trust-plane / 14-domain-audit-coverage / promotion-gate apparatus until the product actually has external users beyond the current 5 and an operator process to match; re-introduce SLOs and formal promotion gates when there's a real second operator or paying-user population that needs them.

## Sequenced transition plan

1. **Week 0 (no code changes, read-only triage)**: Read the 14-row repeat-class table + skim P-entries with 2+ citations in it; draft the ~20-40 "lessons," each mapped to (a) an existing gate that already covers it, (b) a gate that needs writing, or (c) an ADR with no executable form. This is the one-time cost of extracting value before deleting the source ledger.
2. **Week 0-1**: Write the ADRs (should mostly transcribe existing R-rules that are already load-bearing per CLAUDE.md's own R1-R3-and-R27 shortlist plus the repeat-class table's 14 entries) and the single living architecture doc. Do not delete BUG-POSTMORTEM/RULES/QA-CHECKLIST yet — freeze them (stop adding new entries) while the new system comes online, so nothing in flight is lost.
3. **Week 1-2**: Stand up GitHub Issues/Projects for currently-open QA-CHECKLIST items (the ~200 open, not all 731); close the rest as "historical, superseded by [lessons doc]."
4. **Week 2-3**: Consolidate the 129 gates into the pyramid — delete the 6+ meta-gates first (lowest risk, they test governance not product), then merge overlapping browser-check files, then migrate `ci-esm-core-unit-check.mjs`'s assertions into a real test runner incrementally (it's 264KB; do this in batches, verifying nothing behavioral is lost, since this is the single highest-value gate in the repo).
5. **Week 3-4**: Wire Conventional Commits + a changelog generator; stop hand-editing CHANGELOG.md; archive the existing 539KB file as a historical artifact (don't delete — it's real history, just no longer the live document).
6. **Week 4**: Archive (move to a clearly-named `_archive/pre-2026-10-restructure/`, or delete if the ADRs+lessons doc have captured everything of value) the ~30 dated HANDOFF/MASTERPLAN/DIAGNOSIS docs and the frozen ledgers. Merge CLAUDE.md + AGENTS.md into the one ≤150-line file.
7. **Ongoing**: re-evaluate charter formalism (trust planes, promotion gates, SLOs) only when a concrete trigger exists (a 6th+ user, a paying customer, an incident that specifically would have been prevented by a promotion gate) — not on a calendar or "just in case" basis.

This plan is deliberately conservative about *deleting* history — every ledger entry has already been paid for once (someone found the bug, understood it, fixed it); the transition's job is to stop paying the *ongoing* retrieval and gate-maintenance cost of keeping it all live and undifferentiated, not to throw away the underlying lessons.
