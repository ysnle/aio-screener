# AIO Screener — Cloudflare Worker Layer Audit
Date: 2026-09-27. Read-only audit of `aio-proxy` and `aio-screener-data-plane`.

## Scope reviewed
- `cloudflare-worker-proxy.js` (951 lines, root) — CORS data proxy + `/anthropic` server-key AI relay + `/relay` operator-key relay + `/health` + `AIOQuotaDurableObject`.
- `worker/data-plane.js` (238 lines) — "fast quotes" Yahoo-chart cron worker, KV-backed, `enabled:false` in `public-config.json`.
- `worker/wrangler.proxy.toml`, `worker/wrangler.example.toml`, `worker/README.md`.
- `.github/workflows/deploy-ai-proxy.yml`, `.github/workflows/deploy-data-plane.yml`.
- `architecture/worker-endpoints.json`, `public-config.json`, client call sites in `js/aio-chat.js`, `js/aio-data.js`, `js/aio-ui.js`, `js/aio-core.js`.
- `_context/OPERATOR-RUNBOOK.md` (targeted grep) and `_context/RULES.md` (targeted grep, not full 412KB read).
- `git log --follow` on `cloudflare-worker-proxy.js` (22 commits), `gh run list` for both deploy workflows.
- Live probes (12 total, all harmless GET/OPTIONS, no `/anthropic` POST sent, no LLM quota consumed).

**Overall impression**: this is a noticeably more mature/hardened design than a typical hobby CORS-proxy-plus-AI-relay. The comments in the source are unusually candid about the deployment's own limits (Origin spoofability, isolate-local rate limiting, HKG regional-403 issue, WO-1B "app token is not real auth"). Several rounds of hardening are evidenced in-code (P310 recovery, WO-1B, v56 P1145-P1158, P1157 native rate-limit bindings). That said, real gaps remain, mostly matching what the code's own comments already admit.

---

## Findings

### Critical
None found. No open SSRF, no unauthenticated `/anthropic` write path, no secret leakage observed.

### High

**H1. `/anthropic` and `/relay` have no real caller authentication — Origin header + optional client-visible token only.**
- Evidence: `cloudflare-worker-proxy.js:669-670` (`resolveAllowedOrigin(origin, env)` then `env.AIO_APP_TOKEN` check), and the code's own comment at lines 359-362: *"정적 사이트+무료 Workers 구조상 진짜 호출자 인증은 불가능하다... 공개 소스를 직접 읽는 작정한 공격자는 우회할 수 있다."*
- `Origin` is attacker-controlled for any non-browser client (curl, scripts) — confirmed live: my OPTIONS preflight with `Origin: https://evil.example.com` still returned `204` with `Access-Control-Allow-Origin: https://ysnle.github.io` echoed back (the *browser* would block the read due to origin mismatch, but a non-browser client reading the body directly is not blocked by CORS at all — CORS is enforced by the browser, not the server). Actual server-side gating happens inside `handleAnthropic`/`handleRelay` via `resolveAllowedOrigin`, which is a header string compare a curl script can trivially spoof.
- `AIO_APP_TOKEN` is optional, and by design ships in the public client bundle (`js/aio-chat.js` `_aioAppToken()`), so it is a "speed bump," not a secret, exactly as the code documents.
- Impact: anyone who reads the public JS (trivial — it's a GitHub Pages static site) can script requests against `/anthropic` that count against the operator's shared Anthropic quota/cost, up to the per-IP rate limit and the DO daily cap. This is a known/accepted risk per the code's own comments, not a silent one — but it is real and worth restating plainly: **the daily cap (default 300) is the only thing standing between a public curl script and unbounded LLM spend**, and one IP can burn the whole day's cap alone (20/min × cap window).
- Design tension acknowledged in-repo: a real fix needs user accounts/OAuth, which conflicts with the static-site-no-backend premise. Not a bug so much as an architecture limit that should stay visible to the operator (it does, via `/health`'s `appTokenRequired` field).

**H2. Per-IP rate limiting is best-effort / not a real global ceiling; only the DO daily cap is authoritative.**
- Evidence: `cloudflare-worker-proxy.js:244-298` — `rateLimitMap`/`anthropicRateLimitMap`/`relayRateLimitMap` are isolate-local `Map`s; comment at 276-284 candidly states real ceiling was `limit × distinct IPs × live isolates` before v56 added native `ratelimits` bindings (`worker/wrangler.proxy.toml:43-62`). Those bindings are **per-Cloudflare-location**, not global, and `workers.dev` has no zone so a zone WAF rule (mentioned as "recommended" in the file header, lines 16-21) is **not actually available** for this deployment — confirmed also in `_context/OPERATOR-RUNBOOK.md:58`: *"v56 이전의 'WAF 규칙이 실효 상한' 안내는 그 전제가 성립하지 않는 잘못된 안내였다."* So the file's own top-of-file "recommended" WAF section (lines 16-21) is stale/misleading advice that the runbook has already flagged as wrong but the worker source comment hasn't been corrected to match.
- Impact: low practical severity given ~5 users / 2-4 concurrent, but worth noting the documented mitigation (WAF rule) doesn't apply to this deployment topology, and the header comment should be corrected or removed to avoid a future operator "recommending" a rule Cloudflare won't let them attach.

### Medium

**M1. Client-side Sonnet model ID (`claude-sonnet-4-6`) does not match the current model line named in this task's context (`claude-opus-5-5`, `claude-sonnet-5`, `claude-haiku-4-5-20251001`, `claude-fable-5-1`).**
- Evidence: `js/aio-ui.js:343-358` (`LLM_MODELS`) — `haiku.id = 'claude-haiku-4-5-20251001'` (matches current dated Haiku ID) but `sonnet.id` / `'sonnet-thinking'.id = 'claude-sonnet-4-6'`. The worker's server-side default/allowlist (`cloudflare-worker-proxy.js:685`: `if (!/^claude-(haiku|sonnet)/.test(...)) body.model = 'claude-haiku-4-5'`) is prefix-based and would accept `claude-sonnet-4-6` without validating it's a real/current ID.
- The deploy workflow's own smoke test (`deploy-ai-proxy.yml:105`) only exercises `model:"claude-haiku-4-5"` — it never calls the Sonnet path, so a stale/invalid Sonnet model ID would not be caught by CI and would only surface as a live 404/model-not-found error to a real user mid-conversation (Sonnet is reachable from the UI's auto-escalation heuristic in `js/aio-ui.js:415-462` for "deep analysis" queries).
- **Unverified**: I did not call the Anthropic API to confirm `claude-sonnet-4-6` is actually retired/invalid (that would have consumed the operator's paid quota, which this audit was told not to do). Flag as: verify against console.anthropic.com's current model list before next release; if stale, this is a live user-facing failure waiting to happen for every Sonnet-tier chat request, not just a cost/security issue.
- Also worth checking: `claude-fable-5-1` and `claude-opus-5-5` are not referenced anywhere in the client or worker — opus is explicitly blocked server-side (`body.model` regex excludes opus; comment line 49 "opus 차단" = cost protection, intentional), fable is simply unused (not a gap, just unadopted).

**M2. Deploy is `workflow_dispatch`-only — no push-triggered deploy, so worker source changes do not auto-deploy; live revision confirmed lagging repo HEAD.**
- Evidence: `.github/workflows/deploy-ai-proxy.yml:3-4` and `deploy-data-plane.yml:3-4` both declare `on: workflow_dispatch: {}` only — no `push:` trigger on `main`.
- Live confirmation: `GET /health` (probe #1) returned `"revision":"v56.33","sourceSha":"46f2f7815bcc22728658f3a276a780b51e998e95"`, while repo HEAD's `version.json`/`worker/wrangler.proxy.toml` both say `v56.55`. `gh run list --workflow deploy-ai-proxy.yml` shows the last successful run was `2026-09-24T13:55:34Z` (run 36009064079), three days before this audit (2026-09-27), and that commit (`46f2f781`, "fix: stage and validate Masters publication atomically (P1204)") is unrelated to the worker — it's simply whatever commit was HEAD when someone last clicked "Run workflow."
- I diffed `46f2f781..HEAD` for `cloudflare-worker-proxy.js` and `worker/`: **only `worker/wrangler.proxy.toml`'s `AIO_APP_REVISION` string changed** (a version-label bump via `bump-version.mjs`), so there is currently no *functional* drift — the deployed code equals HEAD's code. But this is coincidental, not structural: because deploy requires a human to remember to trigger it, any future functional change to `cloudflare-worker-proxy.js` or `worker/data-plane.js` will sit undeployed indefinitely (there's no CI gate that fails a PR/merge for "worker source changed but not redeployed" — the `ci-cloudflare-deployment-contract-check.mjs` / `ci-external-pipeline-check.mjs` validate config *shape*, not that the running edge matches HEAD, per `_context/OPERATOR-RUNBOOK.md:78`, which itself already flags this: *"자동화하지 않는다면 소스와 라이브 Worker 리비전이 벌어진다."*).
- This is a known, documented limitation (not a silent one), but for a 5-person team with infrequent deploys it's a real operational foot-gun: a security fix landed in the worker source is inert until someone remembers `gh workflow run`.

**M3. `worker/` has two separate wrangler configs and two separate deploy paths for two workers that share one conceptual "edge layer," increasing the chance of divergent tooling.**
- Evidence: `deploy-ai-proxy.yml` uses `worker/wrangler.proxy.toml` directly (with a `sed` SHA substitution to a `.deploy.toml`); `deploy-data-plane.yml` uses `worker/wrangler.example.toml` as a *template*, substituting both `__AIO_QUOTES_KV_ID__` and `__AIO_SOURCE_SHA__` into a generated `worker/wrangler.toml` at CI time (never committed). Both pin `wrangler@4.120.0` explicitly as a global npm install in each workflow (not a `package.json` devDependency — confirmed via `grep wrangler package.json` returning nothing), so a version bump requires editing two YAML files in lockstep; the data-plane workflow's own comment (`deploy-data-plane.yml:38-39,46-48`) documents this exact class of past bug (wrangler 4.44.0 vs 4.120.0 mismatch, Node 22 requirement).
- Not a security issue, but a maintenance/coherence smell: this should be a single pinned `wrangler` devDependency in `package.json` referenced by both workflows via `npm ci && npx wrangler ...`, not two independent global installs.

**M4. `ALLOWED_DOMAINS` allowlist (35 hosts) is a manually maintained list with no automated sync check against actual client usage beyond a comment.**
- Evidence: `cloudflare-worker-proxy.js:89-136`, comment at line 90: *"index.html 실제 호출처와 동기화 (누락 시 CF Worker 경유 403 → 직접 호출 폴백, 설계 무산)"* — i.e., the invariant is documented but enforcement, if any, wasn't located in the scripts I sampled (`ci-worker-anthropic-check.mjs`, `ci-worker-relay-check.mjs` cover `/anthropic` and `/relay` only). If this is not covered elsewhere in the ~30 `ci-*.mjs` scripts (not exhaustively reviewed — most are outside worker scope), the allowlist can silently drift from what the client actually needs, causing either (a) silent fallback to direct calls (defeats the CORS-proxy purpose and exposes user IPs to upstream providers directly) or (b) an over-broad allowlist retained from removed features. Low urgency given the small, stable list, but worth a lint check if one doesn't already exist.

### Low

**L1. Stale/self-contradicting operational advice left in the source header.**
- `cloudflare-worker-proxy.js:16-21` recommends a Cloudflare WAF Rate Limiting Rule as the strong rate-limit backstop, but (per M1/H2 evidence) this deployment is on `workers.dev` with no zone, so that rule is not attachable — and the runbook already says so. The source comment should be corrected to point at the native `ratelimits` bindings (which the file *does* implement further down, lines 276-298) rather than leaving contradictory guidance at the top.

**L2. Bot/UA blocklist is a modest speed bump, easily bypassed.**
- `cloudflare-worker-proxy.js:215-216`: `BOT_UA_RE` blocks `curl/`, `python-requests`, etc. by matching the default UA string — trivially bypassed by setting any `User-Agent` header. Only applies to the generic `?url=` proxy path (not `/anthropic`/`/relay`, which don't check UA at all). Not a real control, just friction against the laziest scanners; fine to keep but shouldn't be relied on.

**L3. `/health` on both workers is unauthenticated and reveals operational metadata (which relay keys are configured, quota-configured booleans, kill-switch state, git SHA).**
- Evidence: probe #1 response includes `sourceSha`, `relay.configured.{fred,bok,kosis}` booleans, `ai.quotaConfigured`, etc. This is explicitly designed as "presence only, never the secret value" (comment lines 367-368, 389, 395-398) and is genuinely useful for CI smoke tests and operator debugging. Flagging only because it's a small amount of infra fingerprinting (exact deployed commit SHA, which relay providers are live) handed to anyone who requests `/health` with any Origin header at all — `/health` does not check Origin (it's excluded from the origin gate at `fetch()` dispatch, lines 813-817). Acceptable for this threat model (5 users, no sensitive data), just noting the surface exists.

**L4. Legal/ToS: proxying Yahoo Finance, Naver, CNN Fear & Greed, CBOE, Stooq, RSSHub, Nitter, Telegram (`t.me`) through a server-side fetch with a spoofed browser `User-Agent` (`cloudflare-worker-proxy.js:905-912`) rather than the requesting user's own client.**
- None of these providers' terms were reviewed in this audit (out of scope / no live ToS fetch attempted). Yahoo Finance's unofficial `query1/query2.finance.yahoo.com` chart endpoints are widely used this way in the OSS community but are not an official public API and can change/rate-limit without notice; server-side proxying with a fixed Chrome UA string is a deliberate anti-block measure (line 906) which nudges this closer to scraping-like behavior than a transparent CORS pass-through. `RELAY_PROVIDERS` (FRED/BOK/KOSIS) are official keyed APIs with clear terms and are lower-risk by comparison. **Unverified** — recommend the operator do a one-time ToS check for Yahoo/Naver/CBOE/Nitter given the shared-key, multi-user (albeit small, 5-person) usage pattern; this is a "confirm you're comfortable with the risk," not a "this is definitely a violation" finding.

## Correctness & robustness notes (not findings, but relevant to the design discussion)

- **Streaming (SSE)**: `fetchAnthropicWithDeadline` (`cloudflare-worker-proxy.js:463-520`) correctly keeps a 60s deadline alive across the full stream lifetime (not just headers), propagates caller abort into the upstream fetch, and cancels the reader on either the caller disconnecting or the timeout firing. This is more careful than most quick CORS-proxy implementations — good.
- **Quota model**: moved from a non-atomic KV get-then-put counter (a documented past bug, `_context/RULES.md:2328`: *"non-atomic race... turned an intended cost ceiling into silent unlimited exposure on the single most common misconfiguration"*) to a single `AIOQuotaDurableObject` with `blockConcurrencyWhile`-guarded reserve/release and idempotency-key dedup (`cloudflare-worker-proxy.js:526-639`). This is a genuinely solid pattern for a low-traffic, single-DO design — atomic, fail-closed if unbound (`hasAtomicQuotaBinding`), self-pruning (`QUOTA_STATE_RETENTION_MS` = 3 days). A single DO instance is a soft bottleneck/single-point-of-serialization, but at 5 users/2-4 concurrent this is a non-issue.
- **Jurisdiction pinning**: the DO explicitly requests a `us` jurisdiction (`state.id.jurisdiction`) and refuses to proxy if it isn't `us` (line 617-619) — a deliberate mitigation for the documented HKG-anycast-403 problem (comment lines 363-366, and confirmed live: **every one of my probe responses' `CF-RAY` headers ended in `-HKG` or `-NRT`**, i.e., Hong Kong/Tokyo edge, consistent with the documented Anthropic regional-403 risk this code works around). This is a well-reasoned, non-obvious fix for a real Cloudflare free-plan anycast quirk.
- **Model allowlist**: `/^claude-(haiku|sonnet)/` prefix match (line 685) is intentionally forward-compatible with dated/未来 model IDs (e.g., would accept `claude-sonnet-5` or `claude-haiku-4-5-20251001` without a code change) — good design choice, opus explicitly excluded for cost control.
- **Body size / response size caps**: 200KB request cap on `/anthropic` (line 675), 5MB response cap on both the generic proxy and `/relay` (lines 782, 925) — reasonable.
- **Error mapping**: `errorResponse()` (lines 321-352) normalizes upstream failures into a client-friendly `aioAiError` envelope with Korean user messages and retry hints — good UX engineering, not just a raw 500 passthrough.
- **CI contract tests**: `scripts/ci-worker-anthropic-check.mjs` imports the actual `cloudflare-worker-proxy.js` module and runs the real `AIOQuotaDurableObject`/`handleAnthropic` logic against fixtures offline (no network) — this is a good pattern (testing the deployed artifact's real code, not a reimplementation) and catches regressions like reintroducing the legacy non-atomic KV path (explicit check: `legacy non-atomic KV handler removed`).
- **`worker/data-plane.js` correctness**: quality/session classification (`CURRENT`/`CLOSED_CURRENT`/`DELAYED`/`STALE`) based on `marketState` + age is sensible; KV write suppression on unchanged revision plus 15-min heartbeat throttling is a thoughtful design to stay under the 1,000/day free-tier KV write limit (documented ceiling: 384/day normal, 576/day worst case) — confirmed live, `/health` showed `coverage 16/16`, snapshot revision fresh (`fetchedAt`/`generatedAt` within the last 5-minute cron tick at probe time).
- **Design coherence — is the mixed-purpose worker a smell?** Combining CORS-proxy + AI-relay + operator-key-relay + health in one Worker is unconventional but the code keeps each concern in its own top-level dispatch branch (`/health`, `/anthropic`, `/relay`, fallthrough proxy) with essentially separate handler functions, separate rate-limit maps/bindings, and separate quota day-keys (`claude:YYYY-MM-DD` vs `relay:<provider>:YYYY-MM-DD`). It's a monolith, but a *reasonably* well-organized one for a project this size — splitting it into 3 Workers would add operational overhead (3 sets of secrets, 3 sets of health checks) that isn't obviously worth it at 5 users. The more interesting design question is **why `aio-screener-data-plane` exists as a second Worker at all when it's currently `enabled:false`** — see below.
- **`aio-screener-data-plane` is functionally complete but administratively unpromoted, not "dead."** It has real Cloudflare Cron (`*/5 * * * *`), real KV writes, passes its own `/health`/`/quotes` smoke tests in CI, and returned live 16/16 Tier-0 coverage in my probe. It is gated off in `public-config.json` (`marketData.fastQuotes.enabled: false`, `soakObservedDays: 0`, `rightsReviewed: false`) purely by policy — `architecture/worker-endpoints.json` explicitly requires a 7-day soak and a rights review before promotion, and states the flag is derived (not hand-toggled) by `scripts/ci-fast-plane-consumer-gate.mjs`. This is a genuinely disciplined "dark launch" pattern, not abandoned code — the caveat is that it duplicates part of what the GitHub Actions `refresh-data.yml` → `public-data/data.json` pipeline (see `reference_data_backend.md` in project memory) already does for the same Yahoo quotes, just on a faster (5-min vs presumably 30-min) cadence for a Tier-0 subset. Once/if promoted, the two data paths (git-committed JSON vs live KV-backed Worker) will need a single documented precedence rule in the client loader; I did not verify whether `js/aio-data.js`'s `_aioLoadServerData` already has that precedence logic (out of scope for this pass — flagging as something the promotion checklist should confirm explicitly, since `_aioLoadServerData` is mentioned in project memory `reference_data_backend.md` as the git-JSON loader and a separate fast-quotes consumer path evidently also exists per `js/aio-data.js:2061-2093`).

## How I would design, deploy, and operate this edge layer instead

The current design is better than its self-deprecating comments suggest, so this is a "sharpen," not a "rewrite."

**1. Split by responsibility, but only two ways, not three.**
Keep `aio-screener-data-plane` (cron + KV, no user-facing auth complexity) as-is — it's already a clean single-purpose Worker. For `aio-proxy`, I would *not* split the CORS data-proxy from `/anthropic`/`/relay` into separate Workers (the operational cost of 3x secrets/health-checks isn't worth it at this scale), but I would extract the shared cross-cutting concerns (Origin resolution, rate-limit enforcement, quota RPC, error envelope) into a small internal module imported by both `cloudflare-worker-proxy.js` and `data-plane.js`, since right now `getCorsHeaders`/`resolveAllowedOrigin`-equivalent logic is duplicated (compare `cloudflare-worker-proxy.js:310-318` vs `data-plane.js:33-43` — same shape, independently written, so a future Origin-list change has to be made twice and could silently drift).

**2. Route framework: Hono.**
Not because raw `switch`-on-`pathname` is broken (it isn't, and rewriting working, well-tested dispatch code for its own sake is a real regression risk given the existing `ci-worker-anthropic-check.mjs` offline contract tests) — but Hono's built-in `cors()` middleware, typed route params, and `app.onError()` would remove ~80 lines of hand-rolled CORS-header duplication and give consistent OPTIONS handling across all four route branches for free. I'd do this only as part of a planned refactor with the existing contract tests as a regression harness, not opportunistically.

**3. Real auth is the one thing worth spending real effort on, and Turnstile is the pragmatic middle ground.**
Short-lived signed tokens minted server-side require a server, which this static-site architecture doesn't have — so the realistic upgrade from "Origin header + optional public token" is **Cloudflare Turnstile**: the client solves an invisible challenge, gets a token, and the Worker verifies it server-side (`siteverify`) before minting a short-lived (e.g., 5-minute) HMAC-signed token that's then required on `/anthropic`/`/relay`. This defeats naive curl-script abuse (the current gap in H1) without requiring user accounts, and Turnstile is free. It does *not* stop a determined attacker who automates solving Turnstile, but neither does anything short of real auth — it raises the bar meaningfully above "read the public JS and set an Origin header," which is the actual current bar.

**4. Per-user quotas via Durable Objects — already 90% there.**
The existing `AIOQuotaDurableObject` is a solid pattern; extending it from a single global daily counter to a per-Turnstile-token or per-session-ID sub-key (still one DO, just a richer `dayKey`) would let the operator give each of the 5 known users their own soft budget instead of one shared pool a single misbehaving script can exhaust. This is a small, additive change to `mutateQuota`'s key shape, not an architecture change.

**5. Cloudflare Cron + R2 instead of git-commit data — reasonable for scale-out, not urgent here.**
The current `refresh-data.yml` → commit `public-data/data.json` pipeline is genuinely fine for a 5-user, ~30-min-cadence app — it's simple, auditable via git history, and free. The Worker-based fast-quote plane (Cron + KV) is the right next step *if* sub-5-minute freshness is actually needed for a subset of tickers, and R2 would only matter if the payload grew beyond KV's per-value size comfort zone (it hasn't — the `/quotes` response was ~9.7KB in my probe). I would not migrate the primary data pipeline off git-commit-to-Pages; I would only finish promoting the already-built fast-quote plane through its documented 7-day soak once the operator has time, since duplicating a second data path is only worth it if it's actually turned on.

**6. `wrangler.toml` as single source, one pinned version.**
Move `wrangler` into `package.json` as a `devDependency` (or an npm-managed tool version file) instead of two independent `npm install --global wrangler@4.120.0` lines in two workflow files (M3 above) — this is a small, low-risk cleanup that removes a whole class of "one workflow updated, the other didn't" bugs the data-plane workflow's own comments show already happened once.

**7. Versioned rollbacks — `wrangler versions`/gradual deployments would be a genuine upgrade over the current all-or-nothing `wrangler deploy`.**
Today, `wrangler deploy` on `workflow_dispatch` is instantaneous and total — a bad deploy is only reversible by re-running the workflow against a previous commit (manual `git revert` + re-dispatch). Cloudflare's `wrangler versions upload` + `wrangler versions deploy --percentage` would let a change roll out to, say, 10% of requests first, and `wrangler rollback` gives a one-command revert without a git operation. At 5 users this is more insurance than necessity, but it's cheap (same free plan) and would directly address M2 — the moment the deploy trigger *is* pulled, having a fast rollback lever matters more, not less, precisely because deploys are infrequent and thus less rehearsed.

**8. Observability: Workers Logs + Analytics Engine over the current print-and-hope.**
`console.error` calls exist (`cloudflare-worker-proxy.js:699`) but I found no `wrangler tail`-based or Logpush-based alerting referenced in the workflows or `_context/OPERATOR-RUNBOOK.md` grep. Cloudflare's Workers Logs (already enabled via `[observability] enabled = true` in both `wrangler.proxy.toml` and the data-plane config, at a 0.1 head-sampling rate) is the free foundation; adding a scheduled Worker or GitHub Action that queries the Analytics Engine/Logs API once a day for 429/503 rate would turn the currently-invisible native rate-limit bindings (explicitly called out as "invisible in the dashboard" in the file's own comments) into an actual signal instead of a black box the operator has no way to notice degrading. This is the single lowest-effort, highest-value addition I'd suggest given the very sound job already done on the write/read-path hardening.

### Trade-offs / free-tier limits to keep in mind
- Workers free plan: 100,000 requests/day, no CPU-time-based billing surprise at 5 users — no concern here.
- KV free tier: 1,000 writes/day per namespace — already engineered around (M docs above), fine.
- Durable Objects on the free plan: included at low volume; a single global DO instance serializes all quota reserve/release calls, which is a non-issue at this concurrency but would need sharding if usage grew 10-100x.
- Turnstile: free, no request limit relevant at this scale.
- `workers.dev` subdomain has no zone, which is precisely why the WAF-rule advice in the source header is stale (L1) — a real custom domain (even a cheap one) would unlock zone-level WAF rate-limiting as an additional, dashboard-visible backstop layered on top of the Ratelimiting bindings already in place. Worth considering purely for that operational-visibility benefit, not because the current bindings are inadequate for 5 users.

## Summary of what's genuinely good here (worth preserving in any redesign)
Jurisdiction-pinned Durable Object quota authority with atomic reserve/release and idempotency keys; SSE relay that keeps the abort/timeout signal alive across the full stream; SSRF/private-IP blocking; a real (if imperfect) Origin+domain allowlist; hardcoded per-provider relay upstreams that structurally prevent `/relay` from being an SSRF vector; offline CI contract tests that import and exercise the actual deployed source; and unusually honest in-code documentation of every remaining limitation. The gaps that exist (H1 auth, M2 deploy-drift risk) are the gaps the code itself already names — the main value-add here is prioritization and a couple of concrete, low-effort next steps (Turnstile, single wrangler pin, Analytics Engine alerting) rather than uncovering anything hidden.
