# X 북마크 추가 열람 D — 성능과 형식 검증

열람일 2026-11-05. 두 북마크 원문과 화면에 표시된 답글 일부를 읽었다. 두 번째 글은 담긴 인용 원문과 첨부 네 장을 모두 직접 화면에서 보았다. 아래 수치·기술 효과는 작성자 진술이며 외부 실험으로 검증하지 않았다. 양 게시물의 전체 댓글·인용·하위 대화는 확인하지 못했다.

## 1. Jarred Sumner: 자료 배치와 성능 최적화

- 북마크: https://x.com/jarredsumner/status/2117037940031496252
- **열람 범위:** 본문 전문, 작성자 후속 답글, 표시된 답글 일부, 인용 목록의 첫 표시분을 읽었다. 원문에 첨부 이미지는 보이지 않았다. 인용 글 일부에 있는 영상·이미지는 시청하지 않았고 194개로 표시된 답글과 전체 인용을 열람하지 않았다.
- **사고 흐름:** 성능을 고칠 때 AI에게 막연히 빠르게 하라고 하기보다 데이터 접근 패턴·배치·메모리 할당 같은 구체적인 가설을 물어본다. 원문은 해시 테이블과 평면 배열, 인덱스와 비트 패킹, 배열의 구조(SoA/AoS), 캐시 제거를 질문한다. 작성자 후속 글은 작은 배열의 할당과 비트셋을 언급한다. 이는 특정 저수준 워크로드에서 검토할 수 있는 설계 후보이지 일반 성능 법칙이 아니다.
- **댓글·인용의 반론:** 한 댓글은 원 데이터 구조 자체를 개선하는 것과 유효한 캐시를 제거하는 것은 별개이며, 캐시가 재계산을 피할 수 있다고 지적한다. 인용 중 한 글은 일괄 캐시 삭제라는 처방을 비판하고, 다른 글은 먼저 프로파일링해 병목을 찾자고 제안한다. 작성자는 다른 대화에서 진행 중인 코드를 표본적으로 살펴보는 자신의 방식을 설명한다. 인용된 ‘10배 빠르게 하라’는 목표는 실측된 개선이 아니다.
- **데이터·논리 평가:** 구체적인 탐색 질문은 유익하지만 원문에는 실행 환경, 입력 크기, 프로파일, 측정 전후, 안전성 검증이 없다. 모든 경우에서 배열이 해시맵보다 빠르거나 캐시가 나쁘다고 결론낼 수 없다. 자바스크립트 엔진의 최적화와 워크로드 특성도 따로 확인해야 한다. 캐시는 정확성·수명·무효화·저장 비용을 포함해 평가해야 한다.
- **AIO 적용:** 성능 작업은 실제 사용자 화면의 부팅·경로 이동·스크리너 정렬·메모리에서 대표 기기/데이터를 프로파일링하고 병목을 찾은 뒤 구조 변경 후보를 비교한다. 동일 데이터·사용 시나리오·기준 기기에서 시간과 메모리, 정확성·회귀를 측정한다. 기존 `src/data/artifact-cache.js`의 캐시를 출처와 신선도 계약 없이 일괄 삭제하지 않는다. 이 자료만으로 성능 결함이나 특정 코드 수정이 확인된 것은 아니다.

## 2. Valentin De Matos가 인용한 lauren의 게임 개발 사례

- 북마크: https://x.com/VDMatos/status/2117051844723720602
- 인용 원문: https://x.com/poteto/status/2117043478140276847
- **열람 범위:** 북마크 원문 전문과 표시된 댓글 일부, 인용된 lauren 글 전문, 그 글에 첨부된 네 이미지와 표시된 댓글 일부를 직접 확인했다. 8개로 표시된 북마크 답글과 인용 원글의 205개 답글 전체, 인용 목록, 게임·코드·모델 명세는 검증하지 않았다. 한 댓글의 8초 영상도 시청하지 않았다.
- **사고 흐름:** 오류를 발견할 때 반복 방지 규칙을 만들고, 상태 기계의 경합을 TLA+로 탐색하며, 실행 예산·재현성·머신 테스트를 함께 설계한다. 작성자는 고빈도 게임 루프와 일반 코드의 경로를 구분한 뒤 할당을 제한하고, 입력에 따른 결정적 재생 및 서버 재검증, 초기 다운로드 크기 예산, 모바일 프레임 목표와 자동 플레이를 설명한다. 소형 게임의 구조를 한꺼번에 보여주는 제작 회고다.
- **첨부:** 첫 장은 최초 커밋 일시를 보여주는 화면이다. 둘째는 자동 선택과 포커스/일시정지의 상호작용에서 실패 상태를 붉은 노드로 표시한 상태 전이도다. 셋째는 여러 게임 상태를 함께 놓고 오류 지점을 번호로 연결한 요약도이며, 넷째는 스토리·텍스트·중단·선택 등 병렬 부분의 전체 상태도다. 작은 글씨 일부는 화면 해상도로 판독하기 어려웠고, 그림만으로 모델과 구현이 일치한다는 점을 검증할 수 없다.
- **댓글·반론:** 북마크의 한 댓글은 실제 플레이 몇 분이면 찾을 수 있는 결함이 남아 있다고 주장하고, 다른 댓글은 많은 PR의 의미를 의문시한다. 이는 독립 관찰의 필요성을 보여 주지만 해당 영상과 게임을 직접 검증하지 않았으므로 결함의 실제 여부는 확인하지 못했다.
- **품질과 한계:** 상태 경합을 반례로 설명하고 성능 목표·예산을 구체화한 전달 방식은 유용하다. PR 수, 짧은 제작 기간, 압축 크기와 프레임 목표는 비교 가능성이 없는 작성자 주장이다. 모델 검증은 모델에 표현된 범위와 가정에 한정되고 실제 UI·데이터·접근성을 자동으로 보증하지 않는다. ‘모든 오류에 린트 추가’나 ‘모든 주석 금지’는 일괄 채택하지 않는다. 반복 위험·유지비용·오탐을 고려하고 복잡한 맥락을 설명하는 필요한 주석은 남긴다.
- **AIO 적용:** 이미 존재하는 모델 검증 범위 및 `model-check` 계약을 먼저 재사용한다. 새 화면 설계에서 경쟁 상태가 중요한 경우(예: 새로고침과 라우트 이동, AI 응답 취소/재요청, 오래된 응답의 덮어쓰기)는 실제 사용자 행동에서 허용 상태·금지 상태·순서·예상 반례를 적고 해당 위험에 비례해 모델 및 브라우저 검증을 연결한다. 설계 문서의 상태도는 이해를 돕는 용도이며 실행 검증 증거와 분리한다. 모의 데이터와 실배포 증거도 분리하고, 초기 다운로드 예산은 AIO의 실제 조건에서 측정하여 정한다.

## 추가 확인

두 건 모두 게시물·댓글이 예시나 경험담이므로, 성능·검증 도구의 실제 효과를 단정하려면 구현 코드·작동 환경·벤치마크와 전후 증거가 필요하다. 이번 작업은 출처 분석 및 설계 제안이며 AIO의 기능 수정이나 브라우저 성능 테스트는 포함하지 않는다.
