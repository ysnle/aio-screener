# 핸드오프 재감사: 설계 선택과 구현 이행 계획

2026-09-21 · Astra 기획·설계·작성. 제품 v56.01. 이 문서는 00–18을 다시 검토한 상위 설계 결정이며 제품 구현 완료나 전역 최적성 증명이 아니다.

## 재감사 판정

기존 자료에는 단일 계산 결과, 입력 시점 계약, publication, 요청 소유권 등 근본 개편안이 있다. 그러나 모든 패키지가 바로 구현 가능한 수준은 아니다. 현재성 판정이 분산돼 있고, 보존을 전제로 한 일부 문구, 추상적인 공통 계약, 대안/비용 비교와 rollback 부족을 보강해야 했다. “문서가 있다”를 “검수가 끝났다”로 처리하지 않는다.

설계 품질은 최선이라는 수사가 아니라 다음 질문으로 평가한다: 어떤 사용자 문제를 해결하는가, 실패를 만드는 소유권을 없애는가, 다른 선택보다 유리한 조건은 무엇인가, 무엇을 잃는가, 실행과 되돌리기가 가능한가, 최종 화면에서 검증할 수 있는가. 비용·사용량·사용자 연구를 측정하지 않은 결정은 잠정안이다.

문서 충돌 시 적용 순서는 **사용자 지시 → 해당 코드 기준선의 실제 증거 → 이 문서의 의사결정 → 개별 과거 설계**다. 문서 번호가 크다는 이유만으로 오래된 증거를 새 증거로 바꾸지 않는다. 발견 ID는 `07:M01`, `05:A04`처럼 패키지와 함께 쓴다.

## 의사결정 비교

첫 파일럿의 **잠정 우선 사용자**는 한국어로 미국·한국 주식을 종가/공시 기반으로 비교하고 연구 논지를 기록하는 자기주도 투자자다. 대표 과업은 ‘선택 기준으로 후보를 줄이고 근거·반증을 확인해 다음 검토 종목을 기록하기’다. 초보 사용자는 같은 근거를 단계적으로 익히고 숙련 사용자는 상세 비교를 펼친다. 기관급 목표는 재현·검토 가능성의 품질 기준으로 적용한다. 초단타·주문 실행·기관 계정 운영을 이번 파일럿의 기준으로 추정하지 않는다. 실제 사용 패턴이 다르면 이 가정을 바꾸고 요구 cadence와 UI를 다시 결정한다.

| 결정 | 검토 대안 | 현재 권고와 이유 | 비용/한계 및 재검토 조건 |
|---|---|---|---|
| D19-1 제품 중심 | 모든 기능 동등 확대 / 연구 과업 중심 | 시장→후보→비교→반증→기록→복기를 기준으로 기능을 선별 | 실제 주 사용자 과업 검증 필요. 기관 업무 전체를 자동 포괄한다고 주장하지 않음 |

| D19-5 검색 보강 | 문장/숫자 직접 덮기 / 검증된 후보 승격 / 공급자 추가 | 대량 공통 필드는 구조화 공급자, 희소 KPI는 18의 후보 승격 | 추출/검토·검색 비용. 동일 결측이 반복되면 전용 adapter로 이동 |

| D19-7 부분 실패 | 전체 중단 / 무조건 부분 발행 / 의존성별 publication | 비교에 필요한 묶음은 고정, 독립 기능은 부분 제공 | 의존성 정의 비용. 결측이 비교집단을 바꾸면 새 run으로 표시 |

기존 Pages·native ESM·EvidenceStore를 고정 조건으로 하지 않는다. 선택한 플랫폼이 위 계약을 충족하지 못하면 교체한다. 반대로 플랫폼 교체만으로 데이터 정의나 금융 타당성이 해결된다고 간주하지 않는다.

## 최소 공통 계약과 소유권

| 객체 | 필수 의미 | 정본 소유자 | 금지되는 대체 |
|---|---|---|---|
| Observation | entity/listing, metric/version, value/unit, period, source, observed/available/retrieved time, quality, supersedes | 데이터 정규화·원장 | 검색 요약을 원값으로 저장; fetchedAt으로 availableAt 대체 |
| PublicationManifest | publicationId, 파일별 content hash/schema, 호환 model/reference revision, 완료 상태 | 발행 coordinator | 개별 latest URL 응답을 호환 묶음으로 추정 |
| AnalysisRun | input refs, universe/filter/model definition, 실행시각, 계산 상태, 결과 | 도메인 실행기 | UI에 보이는 값으로 역산; 새 입력으로 과거 run 재해석 |
| Explanation | runId, 관측/계산/가설 구분, 기여·제외·반증·불확실성 | 도메인 결과+presentation | renderer나 AI가 독자적으로 금융 등급 재계산 |
| ResearchCandidate | 원문 위치·추출 값·검증/검토 상태·충돌 | 검색 보강 job | confidence 숫자만으로 canonical 승격 |
| JobReceipt | 예정시간·시도·성공·보존·실패·출력·도달 | 자동화 운영 | exit 0으로 모든 데이터 현재성 인증 |

모든 객체를 하나의 거대한 저장소로 만들 필요는 없다. entity/observation/run/publication 참조가 도메인 경계를 넘어 끊기지 않는 것이 요구사항이다. private portfolio는 public 원장과 분리하고 공개 산출물에 개인 참조를 넣지 않는다.

연결 키는 다음과 같이 계약한다. `candidateId → observationId`는 검증 결과와 출처 위치를 가진 승격 기록으로 연결한다. 정정은 기존 observation을 덮지 않고 새 ID와 supersedes 관계를 만든다. `jobReceiptId → publicationId`는 검증된 출력 hash 목록을 연결한다. `inputSnapshotId`는 실제 사용한 publication/file hashes, observation IDs, universe/model/definition 버전의 호환 묶음을 고정한다. `runId → inputSnapshotId`, `explanation.runId`, `aiRequestId → runId/evidenceIds`, `claimId → observationId/derivedResultId`를 보존한다. 파생값은 operand ID와 formulaVersion을 가져야 한다. 허용되지 않은 누락 참조가 있으면 해당 승격·설명·claim 공개를 중단한다.

## 실행 순서: 결함 억제와 구조 교체를 병행

1. **현재 반증 재확인·의미 오표시 억제**: 14:T04 주봉 준비 상태, 12:U01 미리보기, 04:C03 집계 범위 등 현재 확정 입력부터 다시 재현한다. 이미 수정된 07:M01/M02/M06 등을 자동 재작업하지 않는다. 데이터/표시의 오해를 막는 작은 수정은 장기 저장소 이전을 기다리지 않는다.
2. **스크리너 한 과업을 끝까지 완성**: definition→snapshot→filter/rank→explanation→저장/replay를 같은 run으로 묶는다. 시작부터 screener/universe/model-validation의 실제 content hash와 호환 버전을 고정하는 최소 manifest를 포함한다. 3단계의 전체 발행 구조 이전을 기다리며 가변 URL의 우연한 조합을 인증하지 않는다. 대상 경계는 `src/domain/screener`, `src/data/providers/screener.js`, `src/data/orchestrators/screener.js`, `src/ui/pages/screener.js`. 최종 owner 하나를 정하고 구 경로를 폐기한다.
3. **발행·자동화 계약 교체**: 17의 domain receipt/SLO/manifest를 구축한다. 먼저 한 projection으로 generation 전환 실패를 검증하고 다른 데이터로 확장한다. 코드 배포와 데이터 갱신 분리는 실측 요구에 따라 수행한다.
4. **기술·AI 연결**: 준비된 run/evidence 계약으로 차트·전략과 AI publication을 연결한다. 모델 정의 변경과 코드 이동은 별도 revision으로 기록한다. 요청 취소/late response는 두 UI에서 같은 계약으로 검증한다.
5. **검색·학습·나머지 기능 확장**: 18의 수직 사례와 13의 연습 사례를 완성하고, 20의 미검수 범위를 순서대로 닫는다. 모든 기능을 공통 객체에 한 번에 이식하지 않는다.

## 대표 구현 작업 카드: 스크리너 의미 단일화

목적: 선택한 프리셋의 기준, 미리보기, 실행 결과, 설명이 일치하고 사용자가 그 이유를 확인한다.

- 소유권: 구현 담당 한 명이 definition/run orchestration과 provider 경계를 소유한다. UI 담당은 해당 계약을 소비하며 독립 필터·rank writer를 만들지 않는다. 공유 파일 수정은 직렬화한다.
- 입력/출력: definitionHash + inputSnapshotId → runId + eligible/filtered/ranked counts + reason codes + explanation. 프리셋 내장 조건과 사용자가 추가한 조건을 함께 노출한다.
- 과거 자료: 기존 saved run을 현재 모델로 묵시 재계산하지 않는다. 구 schema reader를 제한 기간 유지하거나 historical-read-only로 표시한다. migration 실패 시 원본 export를 보존한다.
- 전환: 같은 고정 입력으로 구/신 경로 결과를 비교하되 사용자는 한 writer만 본다. 의도된 수식 차이는 별도 승인된 model revision과 차이표로 남긴다. 단순 수치 일치를 위해 기존 잘못된 의미를 유지하지 않는다.
- 완료: 현재 데이터/선택 정의가 같으면 preview와 execute 판정 집합이 같다. 입력이 바뀌면 새 snapshot임을 표시한다. 상세 기여·제외 이유가 실제 계산과 일치하고 저장 후 replay가 같은 결과를 반환한다.
- rollback: 새 경로가 불완전하면 마지막 호환 publication과 검증된 이전 renderer로 돌아간다. 이미 알려진 잘못된 순위/설명을 정상 상태로 되돌리는 rollback은 금지한다. 필요한 경우 계산 보류와 근거 열람만 제공한다.

## 이행·삭제·복구의 공통 완료 기준

각 패키지는 현재 writer 목록, 최종 owner, 새 계약, 제거할 compatibility 호출, 이전 저장 데이터 처리, 실패시 복구 경로를 코드 근거와 함께 제출한다. 신규 wrapper 존재만으로 이행 완료로 보지 않는다. shadow 비교는 임시이며 종료 기준을 정한다. legacy 코드 제거 후에도 숨은 timer/event가 쓰지 않는지 검증한다.

데이터 migration은 복사본에서 검증하고 원본을 보존한다. 삭제/보존기간·검색 원문 저장 권한·개인정보 보존은 실제 운영 조건에서 정한다. artifact GC는 활성 manifest/저장된 run의 참조를 먼저 확인한다. 이 감사는 실제 삭제나 배포를 승인하지 않는다.

파일럿 구현 전에 retention 계약을 등록한다. 출처별 `canPersistRaw/canRedistribute/retentionUntil/deletionAction`이 없으면 원문 전체의 지속 저장·공개를 기본 허용하지 않는다. 링크·필요한 provenance와 허용된 추출 범위만 보존하며, 이것도 출처 조건에 맞춰 결정한다. public publication은 개인 보유/메모를 포함하지 않는다. 학습용 run은 원본 개인 정보를 자동 복제하지 않고 공개 데이터와 가정만 사용하는 것이 기본이며, 개인 내용이 필요한 복사·AI 전송은 명시적 선택으로 분리한다. 원문 만료/삭제 후에는 dangling reference를 정상 재현이라고 표시하지 않고 tombstone과 재현 가능 범위를 남긴다. 영구 재현 요구와 삭제 의무가 충돌하면 원문 재배포를 우선하지 않는다.

## 사용자 인수: 직관성은 문서만으로 인증하지 않음

서로 다른 숙련도의 사용자에게 동일 과업을 준다: 비교집단/기준일 찾기, 선정·제외 이유 설명, 결측과 낮은 점수 구분, 가정 하나 변경 후 변화 예측, 원문 확인, 과거 run 복기. 성공 여부·오해 유형·도움 요청·완료시간을 기록하고 초기 기준을 측정한다. 목표 시간/성공률은 임의 숫자로 인증하지 말고 이 기준과 제품 요구에서 사전 설정한다.

결정적인 오해(상대 순위를 수익 확률로 해석, 오래된 값을 현재로 해석, 계산 보류를 저평가로 해석)가 관찰되면 해당 과업은 실패다. 설명을 읽었는지보다 실제 다른 사례에 올바르게 적용했는지 확인한다. 키보드·스크린리더 동선도 같은 과업에 포함한다.

## 이번 독립 재검토의 처리 기록

Luna MAX 두 에이전트가 구조/이행과 금융/사용자 의미를 분리 리뷰했고 Astra가 문서를 수정했다. 반영한 항목은 과거 결함의 현재성 안내(03/07/08/09), 구 구현 재작업 지시 제거(01/02), 기존 registry 보존 전제 제거(00), 기관급 라벨의 근거 요건(14), 통화/가격·총수익률 fixture(15), 입력 고정 선행 조건·객체 연결키·retention·우선 사용자·이행과 rollback(19), 대장의 날짜/미리보기 요약 정정이다.

이로써 설계 충돌과 일부 구현 공백을 줄였지만 모든 패키지의 상세 schema/API·자원 비용·실제 사용자 평가가 완료되지는 않았다. 이번 문서 검토는 새로운 제품 함수 전수 실행을 대신하지 않는다. 다음 코드 감사는 20의 큐를 따른다.
